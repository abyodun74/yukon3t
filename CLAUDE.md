@AGENTS.md

## Agent delegation policy

Never do the work yourself directly — always hand every task off to a sub-agent (the `Agent` tool) rather than using your own tools inline. Route by difficulty:

- **Simple/routine tasks** (small edits, verification runs, straightforward fixes): delegate to a Sonnet or Haiku sub-agent.
- **Hard/reasoning-heavy tasks** (architecture decisions, tricky bugs, anything needing careful multi-step thinking): delegate to an Opus sub-agent — the `model` option accepts `"opus"`, which resolves to the current flagship Opus build available to the tool (there is no separately-selectable "Opus 5.5"; ignore that specific name if it's ever requested and use `"opus"`).

### Mobile (Capacitor — Android/iOS wrapper)

```bash
npx cap sync android     # after changing native plugins/capacitor.config.ts
npm run cap:sync:ios     # same, for iOS — NOT plain `npx cap sync ios`, see below
cd android && ./gradlew assembleDebug    # debug APK for sideloading/testing
cd android && ./gradlew bundleRelease    # signed AAB for Play Store (needs android/keystore.properties, gitignored)
```

**Native plugin patches**: `patch-package` (`postinstall` script) reapplies anything in `patches/` after every `npm install` — durable across reinstalls/CI, unlike hand-editing `node_modules` directly. Currently patches `@capacitor/share`'s Android plugin (`patches/@capacitor+share+8.0.1.patch`): its `isPresenting` flag only ever clears when the share sheet's own activity-result callback fires, which doesn't always happen if a share gets abandoned mid-flow (backgrounding/killing the app while the chooser or picked target app is on screen) — every subsequent `Share.share()` call then fails immediately with `"Can't share while sharing is in progress"`, regardless of which post or how much later it's retried. The patch resets the flag in `handleOnStart()` instead, so returning to the app always clears any stale pending share. **Like any native change, this only reaches real users through a new Play Store release** — `src/lib/native-share.ts` also has a web-deployable stopgap (a clearer, actionable message instead of the plugin's raw error text) for the currently-live app in the meantime. If `node_modules/@capacitor/share/android/build/` ever reappears from a local Gradle run, delete it before touching `patches/` again — `patch-package`'s git diff chokes on Windows over the resulting long build-artifact paths.

**Critical**: `capacitor.config.ts` sets `server.url: "https://yukon3t.com"` — the native app's WebView loads the **live deployed site directly**, it does not bundle a local copy of `src/`/`public/`. This means:
- Any change to `src/` reaches mobile users the instant it's deployed to the web (Netlify), no app update needed. **`yukon3t.com` itself resolves to Netlify, not Vercel** (confirmed via response headers — `Server: Netlify`) — when testing a fix on a real device, a `vercel --prod` alone does nothing for it; wait for Netlify's deploy (`git push` auto-triggers it) to reach `state: "ready"` for the right commit.
- Changes to `android/app/src/main/AndroidManifest.xml` (permissions, etc.) or any other native code are baked into the APK/AAB at build time and **only reach real users through a new Play Store release** — pushing to `master` does nothing for these. Bump `versionCode` in `android/app/build.gradle` on every release build (comment there explains the current floor).

## Architecture

**Stack**: Next.js 16 App Router (Server Components + Server Actions), NextAuth v5, Prisma 7 + Postgres (Neon in prod), Tailwind 4, Vitest. Deployed in parallel to **both Vercel and Netlify** off the same repo — see "Dual deployment" below.

### Server Actions are the primary write path

Almost all mutations live in `src/app/actions/*.ts` (one file per domain: `posts.ts`, `messages.ts`, `circles.ts`, `calls.ts`, etc.), not API routes. `src/app/api/` exists mainly for webhooks, cron, and things that must be a real HTTP endpoint (auth callbacks, push). Every action follows the same shape: re-derive the actor from the session server-side, check ownership/membership (`src/lib/auth-guards.ts` + per-file checks), validate input with Zod (`src/lib/validations.ts`), then touch Prisma. Don't skip any of these three steps when adding a new action — it's the established pattern the whole app relies on for authorization.

### Never send a `User` row to a browser

Anything a Server Action returns, a Server Component passes as a prop to a `"use client"` component, or a route handler puts in JSON is serialised to the browser in full, whatever the receiving TypeScript type says. So never return or pass a `User` row fetched without a `select` (directly, nested via `include: { user: true }` / `author: true` / `members: { include: { user: true } }`, or the row `requireUser()` returns): `select` exactly the fields the UI reads, or copy them into a new object first. This applies to the signed-in user's own row too. As a backstop only, the Prisma client (`src/lib/prisma.ts`) omits `passwordHash`, `emailOtpCodeHash`, `passwordResetRequiredAt` and the three hidden-chat PIN columns from every query, and its type says so, so reading one without asking for it is a compile error; `getPasswordHash` (`src/lib/auth-guards.ts`) is how a re-authentication check reads the password hash. Email, phone, birth date, lockout and moderation columns are not omitted and still need the `select`.

### Prisma client has a custom output path

`prisma/schema.prisma`'s `generator client` outputs to `src/generated/prisma`, not the default `@prisma/client` location. Import as `@/generated/prisma/client` (or whatever's re-exported from `src/lib/prisma.ts`), not `@prisma/client` directly. This directory is gitignored — `npm install` runs `prisma generate` via `postinstall`, but a fresh clone or a CI target without that hook needs `npm run db:generate` before anything typechecks.

### pgvector HNSW indexes — Prisma will try to drop them

`Circle`/`CollabBoardPost`/`Post`/`Conversation.embedding` each carry a hand-written pgvector HNSW index (`prisma/migrations/20261010180000_restore_embedding_hnsw_indexes`). `schema.prisma` can't represent them (`embedding` is `Unsupported("vector(1536)")` and Prisma has no HNSW index type), so `prisma migrate dev` sees them as drift and writes a `DROP INDEX` line for each into **whatever migration it generates next** — that's how two earlier migrations silently removed all of them. Generate with `prisma migrate dev --create-only`, delete those `DROP INDEX` lines from the new `migration.sql`, then apply. `scripts/check-migrations-no-hnsw-drop.mjs` replays the migration files (no database needed) and fails `npm test` (via `src/lib/search-embeddings.test.ts`) and every build (first step of `scripts/migrate-if-production.sh`, before `prisma migrate deploy`) if one slips through; to add or remove an HNSW index on purpose, change its `EXPECTED_HNSW_INDEXES` in the same commit. It doesn't catch an index removed implicitly by a `DROP TABLE`/`DROP COLUMN`.

Two things are deliberately *not* index-backed. `User.embedding` has no HNSW index: the presence heartbeat updates `User.lastSeenAt` every 45s per online user, and each of those row updates would insert a fresh 1536-dim entry into it. And the Home feed's category tabs (`nearestPostIds` in `src/lib/search-embeddings.ts`) always run an exact scan even though `Post.embedding` is indexed — an HNSW scan is approximate and returns at most `hnsw.ef_search` rows (default 40) whatever the query's `LIMIT` says, and that result is a membership set for a tab, so dropping a few would make posts vanish from it. Every nearest-neighbor query goes through that file's `approximateNearest` (raises `hnsw.ef_search` via `SET LOCAL` inside a transaction) or `exactNearest`; never write a bare `ORDER BY "embedding" <=> ... LIMIT n` anywhere else.

### `src/proxy.ts` is the middleware

Next.js 16 renamed `middleware.ts` → `proxy.ts` with a renamed export (`proxy`, not `middleware`) — this is a breaking change from older Next.js training data (see `AGENTS.md`). It sets a per-request CSP nonce and builds `connect-src`/`media-src` dynamically from `R2_ACCOUNT_ID`/`R2_PUBLIC_URL` so the CSP only opens up once media upload env vars are actually configured.

### Auth: dual sign-in methods sharing one session mechanism

NextAuth v5 (Resend magic link) is the default, but `src/app/actions/password-auth.ts` implements a **fully custom** username/password path — not NextAuth's Credentials provider, because Credentials doesn't support the status/verification-gated login logic this app needs. Sessions use the **`"jwt"` strategy** (`src/lib/auth.ts`) — despite the schema having a `Session` table (kept for the Prisma adapter's other uses), neither sign-in path writes a row to it. `issueSessionCookie` (`src/lib/session-token.ts`) hand-encodes a JWT identical in shape/secret/cookie-name to the one Auth.js's own `jwt`/`session` callbacks would produce for magic-link/OAuth, so `auth()` reads either path's cookie identically. Because JWTs are stateless, there's no server-side token to revoke on logout or ban/suspend — `requireUser()` (`src/lib/auth-guards.ts`) instead checks `User.sessionInvalidatedAt` against the token's own `issuedAt` claim on every request; setting `sessionInvalidatedAt` (done on password reset and password change) is what actually forces re-authentication, not deleting anything. If you touch session/cookie logic, both paths need to keep working, and any new "kill this session" feature must go through `sessionInvalidatedAt`, not the `Session` table.

**Forced password reset (`User.passwordResetRequiredAt`).** Set by migration `20261011150000_force_password_reset` on every account that had a password while password hashes could reach other users' browsers (see `SECURITY.md`). While it is set, `loginWithPassword` refuses the correct password, emails the normal reset link and redirects to `/sign-in?notice=reset_required`; the decision is the pure `passwordSignInOutcome` (`src/lib/password-sign-in.ts`). Magic link / Google / Apple are unaffected, and existing sessions are not ended. **Every writer of `passwordHash` clears `passwordResetRequiredAt`** (today: `resetPassword`, `setPassword`, `confirmPasswordChangeDeviceChallenge`, `fixAppReviewDemoAccount`, `scripts/fix-app-review-demo-account.ts`) — do the same in any new one. The column is in the Prisma client's global `omit` like `passwordHash`; `isPasswordResetRequired` (`src/lib/auth-guards.ts`) reads it for the signed-in user.

### Device attestation (native sign-up/sign-in) — server half only

Plan: `docs/plans/app-attestation.md`. Phase 0 (web/server) is live in `observe` mode. Phase 1 (the `@capacitor-firebase/app-check@8.5.2` dependency, `patches/@capacitor-firebase+app-check+8.5.2.patch` adding `getLimitedUseToken`, cap sync, App Attest entitlement, Android versionCode 29 / 1.26) is built and committed (2026-10-15) but reaches users only through the Play Store / TestFlight release; no installed app sends a token until then. **iOS ordering:** Firebase fixes the App Check provider when `FirebaseApp.configure()` runs (both Firebase plugins call it from `load()`, in random plugin order), so **every plugin that calls `configure()` must set the factory itself, immediately before that call**, inside its `FirebaseApp.app() == nil` guard: the app-check patch (`FirebaseAppCheck.init`) and `patches/@capacitor-firebase+messaging+8.3.0.patch` (`FirebaseMessaging.init`, whose patched `Package.swift` adds the `FirebaseAppCheck` product) each carry a file-private App Attest factory (debug factory under `#if DEBUG`). Whichever plugin loads first installs it; no cross-module lookup, nothing in `AppDelegate`. Any new native code that calls `FirebaseApp.configure()` needs the same two lines. Setting a factory anywhere later (e.g. JS `initialize()`) is silently ignored and leaves the unregistered DeviceCheck default (`exchangeDeviceCheckToken` in the error text means exactly that).

- **What exists.** Every Turnstile-gated action calls `passesBotGate(formData, ip, action)` (`src/lib/bot-gate.ts`) instead of `verifyTurnstile`. `src/lib/app-attest.ts` verifies the `yk-app-attest` field through `src/lib/app-check-rest.ts` (Google's REST `verifyAppCheckToken`, which consumes the token; 5s cap) using the shared admin app's service-account credential. **Never import `firebase-admin/app-check` or `/auth`** � they pull in `jwks-rsa`, whose require() of ESM-only `jose` crashed every route on Netlify (2026-10-15); `src/lib/no-jwks-rsa-imports.test.ts` enforces it. The shared admin app in `src/lib/firebase-admin.ts` (also used by `fcm.ts`). `src/lib/app-attest-client.ts` reaches the native plugin through `registerPlugin("FirebaseAppCheck")`, every call gated on `Capacitor.isNativePlatform() && Capacitor.isPluginAvailable("FirebaseAppCheck")`, so browsers and today's builds never call anything native. `TurnstileWidget` (in-form) and `useTurnstileGate` handle the modes; `ad-booking-form.tsx` is Turnstile-only (`attest={false}`).
- **Trust rule (don't weaken).** The only way to pass without Turnstile is mode `enforce` AND a valid token, not already consumed, whose `appId` is in `FIREBASE_APP_CHECK_APP_IDS`. Every other path returns exactly `verifyTurnstile(formData, ip)`. `yk-app-meta` (platform/build/plugin, plus optional `e`: a capped, control-stripped, <=260-char failure-reason diagnostic such as `reject:<native error>`, `timeout:<ms>`, `late:<ms>`, `pending`, `init:<msg>` -- telemetry only, read at `metadata.meta.e`), the user agent and the `yk-attest-fallback` cookie are untrusted: telemetry, or a switch to *more* friction, never a pass. An App Check error or timeout is never a pass. Add no attestation bypass for the App Review demo account.
- **Modes** (`NEXT_PUBLIC_APP_ATTEST_MODE`, read by client and server; unset = `off`). `off`: today's behaviour, the token is ignored. `observe`: the app still shows the Turnstile button, may send a token alongside, and the server records an `APP_ATTESTATION` analytics row (outcome, platform, whitelisted meta, Turnstile result) whenever a token or meta is present, deciding on Turnstile only. `enforce`: in the app with the plugin there is no button; a valid token passes, anything else sets `yk-attest-fallback` (30 min, switches the app to the button) and falls through to Turnstile. Inert, with one `console.error`, if the mode is set without `FIREBASE_PROJECT_ID`/`FIREBASE_CLIENT_EMAIL`/`FIREBASE_PRIVATE_KEY`/`FIREBASE_APP_CHECK_APP_IDS`.

### Media uploads: direct browser → R2, never through the Next server

Avatars, post images, and videos upload straight from the browser to Cloudflare R2 via short-lived presigned PUT URLs (`src/lib/storage.ts` mints them server-side; `src/lib/upload-client.ts` does the client-side PUT with retry/timeout logic). This is deliberate — it avoids serverless request-body limits, and images are resized **client-side via `<canvas>`** before upload rather than server-side (no `sharp`/libvips in the untrusted-image path — see `SECURITY.md`). `resizeImageFile`/`captureVideoFrame` in `upload-client.ts` read the canvas output into a plain `ArrayBuffer` before wrapping it in a `File` — this isn't stylistic, it works around a real Android WebView bug where a `canvas.toBlob()` Blob can be backed by an already-invalid temp file, failing instantly with `net::ERR_UPLOAD_FILE_CHANGED` on both the upload PUT and even a same-page `<img>` preview of it.

Real file size is re-verified server-side after upload (`HeadObjectCommand`); a presigned PUT alone can't cap size.

**Every upload path needs its own retry/timeout, not just the browser one.** The native Android video picker (`GalleryPickerPlugin.java`'s `uploadVideo`, see below) streams straight from `ContentResolver` to the presigned URL entirely in Java, bypassing `upload-client.ts` and its `withRetry`/`fetchWithTimeout` entirely — it shipped as a single unretried attempt with no connect/read timeout, and failed outright on a real (not simulated) transient network blip during a longer video upload on live hardware, with no automatic recovery. Fixed with its own bounded retry + timeout loop, but the lesson generalizes: **any new upload path that doesn't go through `upload-client.ts`** (a native plugin, a different platform's picker, a future non-browser client) **needs to reimplement that same resilience itself** — it does not come for free just because the rest of the app has it.

### Profile pictures: not saveable in-app, and private behind `AVATAR_PRIVATE` (staged rollout)

**Deterrent (always on).** No save/download/share control is offered for a profile picture anywhere, including the enlarge view (`profile-story-ring.tsx` opens `Lightbox` with `protect`, which drops its Save button and blocks the context menu on the whole viewer). Every avatar `<img>` (`UserAvatar` in `user-link.tsx`, the story rings in `story-tray.tsx` / `profile-story-ring.tsx`, `ZoomableImage` when protected) spreads `protectedImageProps()` (`src/lib/protected-image.ts`): `draggable={false}`, `onContextMenu`/`onDragStart` preventDefault, and the `.protected-image` class in `globals.css` (no touch callout, selection or `-webkit-user-drag`). Taps still reach the surrounding link/button. The first three also use `useImageFallback` (`src/lib/use-image-fallback.ts`): a picture that fails to load (expired session, rate limit, block, deleted) shows the initial / "No photo", never a broken-image icon. A new surface that shows an avatar should use `UserAvatar` or the same helpers, and never pass an avatar to `saveMediaToGallery`/`shareNative`. The user's own avatar preview/cropper in settings is not protected. FAQ entry: `save-someones-profile-picture`.

**Private storage (flag `AVATAR_PRIVATE=1`, server-read, default off; needs `R2_AVATAR_BUCKET_NAME`, see `.env.example`).** Earlier versions of this section said avatar URLs had to stay public for OG/meta, web push, FCM, notification images and the native apps; that was wrong (checked 2026-10-19: none of those use an avatar URL, and the WebView loads the site same-origin, so its cookies reach `<img>`). The only reader outside the signed-in app is the bearer-token widget feed `GET /api/ambient/feed`. Pure rules are in `src/lib/avatar-url.ts`, the server half in `src/lib/avatar-storage.ts`, bucket functions at the end of `storage.ts`:
- **Bucket.** A third R2 bucket with no public domain, never the view-once one (its required 15-day lifecycle rule would delete every avatar). Browsers get 5-minute presigned PUTs for `avatar-upload/<userId>/<uuid>.<ext>` keys only (`PrivateObjectPurpose` `"avatar-upload"`); the served keys `avatar/<userId>/<uuid>-t.<ext>` (~320px thumbnail) and `-f.<ext>` (~1080px) are written by `confirmPrivateAvatarUpload`'s server-side copy, so a still-valid PUT can't swap the picture after moderation. Both images are size/type-checked and moderated (two `moderateImage` calls through 5-minute presigned GETs).
- **Stored value.** `User.avatarUrl` = `/api/avatar/<userId>/<uuid>-t.<ext>` (same-origin, relative). The backfilled form `/api/avatar/<userId>/<uuid>.<ext>` is one image for both sizes.
- **Route** `src/app/api/avatar/[...key]/route.ts`: 401 without a session (`auth()` JWT, no DB read), strict key validation (`parseAvatarRouteSegments`; the `-f` file is never addressable by path), per-user `avatarView` limiter (600/h), 404 if blocked either way, then a 302 to a presigned GET signed at the start of the hour (2h expiry, so the URL is stable and browser-cached for the hour; the redirect is `Cache-Control: private, max-age=3000`). Bytes never stream through the server. `?size=full` (`avatarFullSizeUrl`, used by the profile enlarge view) serves the full image only to the owner and accepted connections; anyone else is redirected to the thumbnail. A qualifying full-size request (and only that) HEADs the `-f` object first; if it is missing or the HEAD fails, the viewer gets the thumbnail under a 60s redirect max-age (`avatarServedObject`) and the route logs `[avatar] full-size object missing`. Without `R2_AVATAR_BUCKET_NAME` it answers 503 (after the 401), logged once per server instance. The path ends in an image extension, so `src/proxy.ts`'s matcher skips it (no page-limit cost per avatar).
- **Consumers outside the app** must not get the relative form: the widget feed uses `avatarUrlForExternalClient` (absolute presigned thumbnail), `exportMyData` uses `absoluteAvatarUrl`. In-app Server Actions (`actions/ambient.ts` etc.) keep the relative form, which the signed-in WebView loads. `src/lib/avatar-exposure.test.ts` fails if a public page or an unauthenticated API route renders/returns avatars. Previous-avatar deletion goes through `deleteStoredAvatar` (public or private, owner's keys only).
- **Flag semantics.** The flag only picks the upload path (`AvatarUpload`'s `privateUpload`, from `isAvatarPrivateUploadEnabled()` on the profile page). Serving needs only the bucket, so turning the flag off never breaks a private picture. Flag off = the public path as before (plus the 2026-10-19 fix: `confirmAvatarUpload` derives the URL from the caller's own key instead of trusting the client's, see `SECURITY.md`). The privacy-policy paragraph and the extra FAQ paragraph (`src/app/faq/content/private-avatars.ts`) render only while the flag is on.
- **Rollout stages.** 1: deploy with the flag off (no change), create the bucket, set the env on Vercel and Netlify, flip the flag. 2: `npm run db:migrate-avatars-private` (dry run, then `-- --apply`, small `--limit` first) copies public avatars to the private bucket under the same key and rewrites `avatarUrl`; it writes an old->new mapping file and never touches the public objects; `npm run db:revert-avatars-public -- --in <map> --apply` undoes it. 4 (built with 1): two sizes for new uploads only; migrated avatars stay single-image because resizing needs decoding untrusted images on the server (no sharp/libvips). **Not built:** Stage 3, deleting the public `avatar/` objects (only once the backfill has been re-run with nothing left and the mapping is no longer needed for a revert), and Stage 5, Android `FLAG_SECURE` / native protection. **When Stage 3 is done, remove the `AVATAR_PRIVATE` flag and the public avatar upload path (`confirmAvatarUpload`, the `avatar` kind's public presign) outright**: the flag is a staged-rollout switch, not a long-term fallback.
- **Limits (say so, don't oversell):** screenshots and devtools still work for anyone signed in who is shown a picture, and a presigned link works for whoever holds it until it expires (at most 2h). The route doesn't check `sessionInvalidatedAt`. The two sizes come from the uploader's browser (a modified client can make a large "thumbnail", capped at 2MB). Until Stage 3, a migrated avatar's old public URL still works for anyone who already has it. Deleting an account doesn't delete its avatar objects (public or private), as before.

### View-once ("for your eyes only") photo/video messages

1:1 chats only. The file never touches the public bucket: it goes browser → presigned PUT → a **second, private R2 bucket** (`R2_PRIVATE_BUCKET_NAME`, same account/credentials; no public domain; CORS for PUT+GET from the site origins; a 15-day lifecycle rule — full list in `.env.example`). `isViewOnceConfigured()` (`storage.ts`) gates everything: unset, the composer's "View once" switch isn't rendered (`viewOnceAvailable` from `messages/[id]/page.tsx`) and the actions return `unavailable`.

- **Model.** `Message.viewOnce` / `viewOnceOpenedAt` / `viewOnceExpiresAt` (sent + 14 days). `mediaType` is `IMAGE`/`VIDEO`, `content` is always `""` (no captions; `editMessage` refuses), and **`mediaUrl`/`mediaThumbnailUrl` stay NULL**. The object key exists in exactly one place, `ViewOnceMedia` (PK `messageId`, cascade). Never `include`/`select` `viewOnceMedia` in a query whose result reaches a browser — that the key isn't on the `Message` row is what keeps it out of every existing message query, `exportMyData`, reply quotes, the inbox preview, the lightbox, push payloads and the moderation queue without touching any of them.
- **Keys.** Two namespaces. *Upload* keys are `view-once/<uploaderId>/<uuid>.<ext>` (and `view-once-frame/…` for a video's still frame), minted by `createPrivateUploadUrl`; `isPrivateKeyOwnedBy` must pass before any R2 call on a client-supplied key, and only these two prefixes can pass it. A *sent* file lives under `view-once-final/<conversationId>/<uuid>.<ext>` (`viewOnceFinalKey`), chosen by the server at send time: no browser is ever given that key or an upload URL for that namespace (`PrivateObjectPurpose` doesn't include it), which is the point — the sender's presigned PUT for the upload key stays valid for up to 30 minutes and could otherwise replace the object after it was checked. `ViewOnceMedia.objectKey` is always a final key.
- **Actions** (`src/app/actions/view-once.ts`; rules and constants in the pure, unit-tested `src/lib/view-once.ts`): `requestViewOnceUpload` (member of a 1:1, not blocked, allowed type, size cap — images 25MB, **videos 64MB** because the recipient holds the whole file in memory) → `sendViewOnceMessage` (re-checks all of that, HEADs the upload for real size/type, server-side-copies it to its final key (`copyPrivateObject`), HEADs the copy — same ETag and size as the upload it just checked, type and size cap enforced again, otherwise both are deleted and the send refused — deletes the upload key, moderates **from the copy**, then creates the `Message` and its `ViewOnceMedia` in one nested create and runs the shared `afterMessageSent`, `src/lib/after-message-sent.ts`; every refusal deletes only this request's own upload keys and copy, so re-submitting an already-sent upload key can't touch a live file) → `getViewOnceContentType` (recipient only, gated like opening, returns just the MIME type: the viewer's pre-check, below) → `openViewOnceMessage` (recipient only; atomic claim `updateMany … where viewOnceOpenedAt: null`; returns a 60s presigned GET; a repeat call re-issues a link only within `VIEW_ONCE_RETRY_WINDOW_MS` (2 min) of the first open and only while the object still exists; publishes the conversation signal so the sender's chip flips to "Opened") → `finishViewOnceMessage` (recipient only, opened only; idempotent). Every deletion goes through `destroyViewOnceMedia` (`src/lib/view-once-media.ts`): object first, row only once R2 confirmed, so a failed delete leaves the row for the sweep to retry.
- **Moderation is not skipped, and is stricter than elsewhere.** A photo is checked itself, through a 5-minute presigned GET handed to `moderateImage`; a video by one still frame the sender's app captures and uploads as a companion object, deleted as soon as it's been checked (the same client-frame stand-in ordinary video messages use, with the same weakness: the client chooses the frame). Unlike every other surface, a video with no usable frame is refused (`frame_required`) and a moderation-API outage refuses the send (`moderation_unavailable`) instead of failing open — there will be nothing left to review afterwards.
- **Sweep.** `sweep-view-once` cron (`src/app/api/cron/sweep-view-once/route.ts`, every minute via `netlify/functions/sweep-view-once.mts`; answers 200 `{ skipped: true }` while the private bucket isn't configured), up to 100 per run: opened more than `VIEW_ONCE_SWEEP_AFTER_OPEN_MS` (4 minutes) ago (finish never arrived), unopened past `viewOnceExpiresAt`, or deleted-for-everyone / moderation-`REMOVED` with a row still present. The 4 minutes are the 2-minute retry window + the 60s life of a link re-issued at its last moment + a 1-minute margin: a shorter cutoff deletes a file a valid link still points at, so change those constants together (`viewOnceMediaIsDue` is the same rule). `deleteMessageForEveryone` deletes it directly; `openViewOnceMessage` also deletes on an "already viewed"/"expired" answer, but only once `viewOnceMediaIsDue` says so, for the same reason.
- **Client.** `chat-thread.tsx` renders a chip instead of media (`viewOnceState`/`viewOnceLabel`); `view-once-viewer.tsx` is confirm → pre-check → open → fetch into memory → show from a `blob:` URL → finish, revoked on close, on `visibilitychange` → hidden (only once showing: never while still downloading), and on unmount. The pre-check (`getViewOnceContentType` + `viewOnceCanPlay`) runs **before** the claim: a video type the device's `canPlayType` rejects (an iPhone `.mov` on most non-Apple browsers) shows "This video can't be played on this device. Open it on another device." and the view is not used. `finishViewOnceMessage` is called only when the media has actually rendered (`load` on the image, `loadeddata` on the video), or when the viewer closes or the element errors after a claim — not as soon as the bytes arrive. It is `aria-modal` (nav.tsx's swipe listener skips it) and `ph-no-capture`, has no save/share/download control, and blocks the context menu, drag and long-press callout. The presigned host is the R2 API host already in the CSP's `connect-src` (path-style URLs), so `src/proxy.ts` needed no change.
- **What it guarantees:** once viewed, the stored file is deleted — immediately in the normal case, within ~5 minutes (2-minute retry window + 60s link + 1-minute margin + 1-minute cron) if the recipient's app never confirms — and no server path can produce it again; nothing is kept for moderators; the bytes are never in the DB backup (only the `ViewOnceMedia` key row, while it exists). **What it doesn't:** it can't stop a screenshot, screen recording, a second camera, or a modified client keeping the bytes it was legitimately sent (native screenshots in a conversation already notify the other person via `ScreenshotGuard`); during the 2-minute window the recipient can fetch the file more than once; the `Message` row (sent/opened timestamps) is permanent; and a file orphaned without ever being attached or swept — an upload never sent (or whose key couldn't be deleted after the copy), or a row cascaded away by an account/conversation delete — is unreachable (no key anywhere) but physically remains until the bucket's 15-day lifecycle rule, which is why that rule is required, not optional.

### Hidden chats (PIN-locked, one-sided)

A user can move any conversation (1:1 or group) into a hidden area that only opens with a PIN. It is per member and one-sided: nothing changes for anyone else in the chat, and nobody is told. It is independent of secret chats (E2EE): hiding doesn't encrypt anything, a secret chat isn't auto-hidden, and the PIN has nothing to do with the E2EE passphrase.

- **Model.** `ConversationMember.hiddenAt` (same per-member pattern as `e2eeEnabledAt`; index `(userId, hiddenAt)`). `User.hiddenChatsPinHash` (bcrypt via `src/lib/passwords.ts`, 4–8 digits), `hiddenPinFailedAttempts`, `hiddenPinLockedUntil`. **Those three `User` columns are omitted from every query by the Prisma client's global `omit` (`src/lib/prisma.ts`)**, because whole `User` rows travel freely here (`requireUser()`, pages, some Server Action results); `getHiddenPinState` (`src/lib/hidden-chats.ts`) is the only reader and selects them by name. Don't remove that omit, and never return that object to a browser.
- **Files.** `src/lib/hidden-chats-rules.ts` is pure and client-safe (PIN pattern, lockout maths, `hiddenPushPayload`, `splitHiddenRecipients`, `isHiddenNotification` / `visibleNotificationWhere`, `hiddenUnlockPath` / `safeHiddenNext`, `HIDDEN_CALLER_NAME`); `src/lib/hidden-unlock-token.ts` is the signed cookie token; `src/lib/hidden-chats.ts` is the server half (queries, cookie, PIN check); actions are in `src/app/actions/hidden-chats.ts`; UI is `/messages/hidden` (`hidden-chats-panel.tsx`, `hidden-pin-field.tsx`), the "Hide chat" / "Unhide chat" item in `chat-options-menu.tsx` (now on group chats too) and `hidden-relock.tsx`.
- **The filter helpers.** `getHiddenState(userId)` → `{ conversationIds, peerIds }` (one query, memoised per request with React `cache`), also as `getHiddenConversationIds` / `getHiddenPeerIds`. A "hidden peer" is the other member of a hidden **1:1**; hiding a group hides the group, not its members. `getMembersHidingConversation(conversationId, userIds)` answers "which of these recipients hide this chat". For a conversation list, filter in the query itself: `members: { some: { userId, hiddenAt: null } }`.
- **The rule: every new surface that lists conversations, peers, or message notifications to a user must apply the hidden filter**, and every new action that takes a conversation (or message) id from the client and reads or writes that chat must refuse with `hidden_locked` when `isMembershipLocked` / `isConversationLocked` says so. Covered today:
  - Conversation lists: the inbox and the hidden list (`getInboxItems` in `src/lib/inbox-items.ts`, `"visible"` / `"hidden"`), `getMyConversationsForShare`, `getShareableConversations` (stories). Share pickers never offer a hidden chat, unlocked or not.
  - Badges and bell: `/api/badge-counts` (unread chats, bell count and the pending-connections count) and `/notifications`, both through `visibleNotificationWhere`. That hides every row tied to a hidden conversation, plus `MESSAGE` / `MISSED_CALL` / `SCREENSHOT_TAKEN` rows whose actor is a hidden peer (`HIDDEN_PEER_NOTIFICATION_TYPES`); a hidden peer's public activity (likes, comments, posts) is deliberately still shown.
  - Peers: the three Connections lists and their counts (`connections/page.tsx`, `loadMore*Connections`, `getAcceptedConnectionIdsByActivity`), `getMyConnectionsForPicker` (live-stream audience and add-to-call pickers), the new-group and add-group-members pickers, both Collab invite pickers, inner-circle candidates / list / ambient feed and the widget feed route.
  - Notifications sent: `afterMessageSent` splits recipients; one who hides the chat gets `hiddenPushPayload()` ("YuKon3t" / "You have a new notification", opens `/home`) on web push and FCM (`type: "GENERAL"`, no conversation id in the data) and **no `MESSAGE` row**; if the lookup fails everyone gets the generic push but the `MESSAGE` rows are still written for all of them (the bell filters a hidden chat's rows at read time, so nobody loses their bell entry and nobody hiding the chat sees one). `replyToStory`'s push and the screenshot notice (`actions/screenshot.ts`: row kept, since the bell filters it, push generic) do the same.
  - Calls: `maskHiddenCallerName` makes the web push, FCM and VoIP ring payloads and `getIncomingCall` say "Private call" for a hidden peer (in `startCall` and `inviteToCall`); `notifyMissedCall` still clears the ring but leaves no named push and no `MISSED_CALL` row.
  - Thread access: `messages/[id]/page.tsx` redirects to `/messages/hidden?next=…` when hidden and not unlocked, which is also what makes "Message" on a hidden peer's profile (and any other deep link) land on the PIN prompt. `hidden_locked` is returned by `sendMessage`, `getConversationMessages` (before it marks anything read), `deleteMessageForMe`, `editMessage`, `toggleMessageReaction`, `suggestCorrection`, `removeCorrection`, `deleteMessageForEveryone`, `shareMuseToConversation`, `requestViewOnceUpload`, `sendViewOnceMessage`, `getViewOnceContentType` and `openViewOnceMessage`; `shareStoryToConversation` and the E2EE actions answer `not_found`. `finishViewOnceMessage` is deliberately not gated (an opened file must still be deleted). `chat-thread.tsx` turns `hidden_locked` into a redirect to the PIN prompt and back, with the typed text kept as the draft.
  - Data export: `exportMyData` (`actions/profile.ts`) leaves out, unless the PIN unlock is live (`isHiddenUnlocked`), messages sent in a hidden conversation, connections with a hidden peer, and reports filed about a hidden peer or about a message in a hidden conversation. Anything added to that export that is tied to a conversation or a peer needs the same filter.
  - Not filtered, on purpose: public search, Discover, People you may know, the public profile and its subscriber lists, posts/comments/likes, admin tools, and group-management actions (rename, leave, add members). `markMessagesDelivered` still marks hidden chats delivered, because the other person must see no difference.
- **Unlocking.** `unlockHiddenChats(pin)` sets `yukon3t.hidden-unlock`: an Auth.js-encoded token under its own salt (same pattern as the pending-login cookie in `device-challenge.ts`), httpOnly, secure, `sameSite: "strict"`, 10 minutes, fixed (activity doesn't extend it), bound to the user id (`isHiddenUnlocked(userId)`). It is cleared by "Lock now", on sign-out (`signOutAction`), after a PIN reset, and by `HiddenRelock` (mounted on `/messages/hidden` and on an unlocked hidden thread) via `navigator.sendBeacon("/api/hidden-chats/lock")` on `visibilitychange` → hidden, except while a native picker is open (`isNativePickerActive`), which hides the page the same way.
- **Lockout is in the database**, because the Upstash limiter fails open (`hiddenPin` is applied only as a second layer). `checkHiddenSecret` counts the attempt *before* checking the secret, in an `updateMany` guarded on the count it read, so parallel guesses get no extra tries. Every 5th wrong attempt since the last correct one locks: 15 min, then doubling up to 24h (`hiddenPinLockoutUntil`). A wrong account password in `resetHiddenPin` counts against the same lock.
- **Forgot PIN.** With an account password: `resetHiddenPin(accountPassword, newPin, confirmPin)`. Without one (magic-link / OAuth only): `requestHiddenPinResetCode` → `resetHiddenPinWithCode`, the emailed `SecurityChallenge` code with the new purpose `HIDDEN_PIN_RESET` (its email says nothing about what the code is for). Chats stay hidden either way.
- **Nothing may hint at use.** The Settings → Privacy "Hidden chats" row and the long-press on the "Messages" heading (`messages-heading.tsx`) are there for everyone and identical in every state; there is no count, dot or indicator for hidden unread anywhere. `hideConversation` answers `no_pin` rather than the page being told whether a PIN exists. Don't add anything conditional on having a PIN or a hidden chat outside `/messages/hidden`.
- **Known limits.** Notifications already delivered before hiding aren't recalled. After answering a "Private call" the in-call UI can show the real name. A hidden peer still appears on public surfaces, and their public activity still notifies by name. The `/messages/hidden` page itself shows "choose a PIN" vs "enter your PIN". A 4–8 digit PIN is only as strong as the lockout: its hash is trivially brute-forced offline by anyone holding the database.

### Native iOS plugins (Capacitor) — `packageClassList` gotcha

`ios/App/App/ScreenCaptureGuardPlugin.swift`/`.m` and `NativeCallKitPlugin.swift`/`.m`/`NativeCallManager.swift` are local plugins (no npm package of their own) declared directly in the App target via the classic Objective-C `CAP_PLUGIN` macro — the same pattern any Capacitor plugin uses. **This is not enough on iOS.** Unlike what the macro's own naming suggests, Capacitor iOS does not discover plugins via an Objective-C runtime class scan: `CapacitorBridge.swift`'s `registerPlugins()` only ever registers a fixed set of built-ins plus whatever class names are literally listed in `ios/App/App/capacitor.config.json`'s `packageClassList` array — and that array is generated by `npx cap sync ios` purely from npm-installed `@capacitor/*` packages' own metadata. A local, non-npm plugin's class name is never added to it automatically, no matter how correctly the Swift/Objective-C side is written. The symptom is exactly what a genuine native bug would look like — `"pluginName" plugin is not implemented on ios"` thrown from the JS side, `load()` never printing anything, even though the class compiles and is wired into the Xcode project correctly — so this is easy to chase as a Swift bug for a long time before realizing it's a registration-list problem instead.

The fix needs the plugin's exact Swift/Objective-C class name (not the JS-registered name, e.g. `NativeCallKitPlugin` not `NativeCallKit`) added to `packageClassList` in `ios/App/App/capacitor.config.json` — but that file is gitignored and fully regenerated by every `npx cap sync ios`, which would silently drop any hand-added entry on the next sync. **Use `npm run cap:sync:ios` instead of plain `npx cap sync ios`** — it runs the normal sync and then `scripts/fix-ios-package-class-list.mjs`, which re-adds `ScreenCaptureGuardPlugin` and `NativeCallKitPlugin` to the list every time. Add any future local (non-npm) iOS plugin's class name to that script's `LOCAL_PLUGIN_CLASSES` array, not just to the generated JSON directly.

`ios/App/App/capacitor.config.json` also doesn't reliably pick up every root `capacitor.config.ts` change on sync either (confirmed live: `ios.contentInset` stayed on a stale `"automatic"` in this file long after the root config moved to `"never"`, even across a fresh sync) — after any sync, diff this file against `capacitor.config.ts` rather than assuming they match.

**Running `npm run cap:sync:ios`/`npx cap sync ios` on this Windows dev machine writes Windows-style backslash path separators into `ios/App/CapApp-SPM/Package.swift`'s `.package(path: ...)` entries** (a real Capacitor CLI bug; Swift only accepts `/`). `scripts/fix-ios-spm-package-names.mjs`, chained into `npm run cap:sync:ios`, now normalizes them to forward slashes, so no manual post-sync check is needed (plain `npx cap sync ios` still leaves them broken). Android's gradle files are not affected.

**SwiftPM identity collision (`app-check`).** SwiftPM takes a local package's identity from the last path component, ignoring `name:`. `node_modules/@capacitor-firebase/app-check` therefore has identity `app-check`, the same as the remote google/app-check package that firebase-ios-sdk needs, so it shadowed it and `xcodebuild -resolvePackageDependencies` failed ("product 'AppCheckCore' ... not found in package 'app-check'"). The same script copies the patched plugin to `ios/App/LocalPackages/CapacitorFirebaseAppCheck/` (gitignored, regenerated every sync) and repoints the manifest there. Xcode/Codemagic must run `npm run cap:sync:ios` first (Codemagic already does). Any new plugin whose directory name equals a remote package identity of its dependencies needs an entry in the script's `RENAMES` table.

### Moderation gate

Post/bio/message text goes through OpenAI's moderation endpoint before being stored visible (`src/lib/moderation.ts`); flagged text is stored as `FLAGGED`, not shown. Images and video-thumbnail frames go through the same endpoint's image moderation and are rejected/deleted outright (stricter than text — no pending state). New user-generated text or media surfaces should go through this, not bypass it.

Post videos over Hive's 60s scan limit (`HIVE_VIDEO_MODERATION_MAX_SECONDS`, `src/lib/storage.ts`) can't get Hive's synchronous body scan, so they get a second, separate automated pass instead: `src/lib/video-review.ts`, driven by the `moderate-long-videos` cron. Whether that pass runs *before* or *after* the post is publicly visible depends on length: from 60s up to `VIDEO_INSTANT_PUBLISH_MAX_SECONDS` (10 minutes) a post publishes immediately (`moderationStatus PUBLISHED`) and is removed after the fact if the pass comes back flagged — same "publish now, react if flagged" model the sub-60s Hive path and text moderation already use; only past 10 minutes does a post still publish hidden (`moderationStatus FLAGGED`) pending that same pass. Either way, `Post.videoLongReviewNeeded` (tracked independently of `moderationStatus` — see the migration adding it) is what the cron's candidate query actually keys on, not `moderationStatus`, since a PUBLISHED post in the instant-publish range still needs the pass to run. This deliberately does **not** run ffmpeg (or any native media binary) on the untrusted uploaded file — same reasoning as avoiding `sharp`/libvips on untrusted images (see `SECURITY.md`), just for video's larger CVE surface. Instead `src/lib/cloudflare-stream.ts` uploads the video to Cloudflare Stream, which is the actual decode boundary; this app's own code only ever touches Stream's own well-formed API output (thumbnail-at-timestamp images fed straight into `moderateImage`, and an AI-generated WebVTT transcript fed into `moderateText` plus a plain wordlist profanity check in `src/lib/profanity-wordlist.ts`, since OpenAI's moderation categories don't cover mere cursing). A flagged video is deleted outright (`removeModeratedContent`) regardless of whether it was already publicly visible or still held — not left in the admin queue like a caption/thumbnail flag; the uploader is told why via `notifyVideoModerationFailed` (`src/lib/video-moderation-notice.ts`), naming the specific violation type(s).

This pipeline is tuned to reach a verdict as close to real time as Cloudflare's own copy/encode/caption processing allows: `createPost` (`src/app/actions/circles.ts`) kicks off the Cloudflare Stream copy the moment the post is created rather than waiting for the cron to discover it, and the cron route (`src/app/api/cron/moderate-long-videos/route.ts`) actively polls each claimed post's progress for up to ~4.5 minutes per tick (`reviewOnePost`) instead of advancing one step and returning — so most videos reach a verdict within a single tick. The cron itself runs every minute and is now just the backstop that resumes a review still in progress past its tick's budget, or one whose eager kick-off never landed — not the primary driver of latency the way it was when it ran every 5 minutes and advanced exactly one post by one step per tick.

### Calls: Daily.co

`src/lib/daily.ts` (server) creates/tokens Daily.co rooms via their REST API — there's no hand-rolled WebRTC, but there are three different front ends on top of it. Sessions that must survive navigation are mounted in one place (`GlobalCallFrame`, root-rendered in `layout.tsx`, driven by `CallSessionProvider` in `src/lib/call-session.tsx`): **1:1 calls** use `src/components/direct-call-frame.tsx`, a hand-built UI on `DailyIframe.createCallObject()` (`renderer: "direct"`); **live streams** use `live-video-frame.tsx`, also a call object (`"custom"`); only **Collab** (and Circle voice rooms, which mount their own in `circle-voice-room.tsx`) still use `src/components/call-frame.tsx`, Daily's prebuilt UI via `DailyIframe.createFrame()`. Because that prebuilt UI lives in a cross-origin `*.daily.co` iframe, both `next.config.ts`'s `Permissions-Policy` (must use `camera=*, microphone=*`, not `(self)` — Permissions-Policy can't wildcard subdomains the way CSP can) and `src/proxy.ts`'s CSP `frame-src` need to allow it, or calls silently break.

**A 1:1 call dropping out of the Daily room is not a hang-up.** It used to be: any `left-meeting` ran `endCall`, which marks the row `ENDED` and deletes the room for both people, so one side's network blip (or backgrounded app) killed the call for both. Now the only intentional exit is `hangUp()` on `CallSessionContext` (the in-call buttons), which ends the session directly without going through a Daily event — so `DirectCallFrame` can treat every `left-meeting`/`error` it sees as involuntary. iOS's CallKit End button is deliberately **not** mapped to `hangUp()` mid-call (`incoming-call-listener.tsx`'s `callDeclined` handler stays decline-only): the side/lock button ends a CallKit call on the earpiece, and an in-app Accept leaves the CallKit banner ringing where a later Decline would hang up the call just answered — don't wire it up until that's been verified on a real iPhone. The rules and every constant are in `src/lib/call-resilience.ts` (pure, unit-tested); change them there, together:

- **Reconnect** — on an involuntary leave, show "Reconnecting…" and retry `join()` on the same call object with the same room URL/token, backing off 1s→8s, for `CALL_RECONNECT_WINDOW_MS` (60s). Before each attempt it asks the server whether the call row is already over (`StartSessionInput.isOver`) and ends without retrying if so; likewise for any Daily fatal error other than `connection-error` (`ejected`, `no-room`, `exp-room`, …: the room or token is gone). Every such status check is capped at `CALL_STATUS_CHECK_TIMEOUT_MS` (3.5s) and no answer means "not known to be over, carry on" — it must never be what holds up a rejoin or an ending. Only when the window runs out does it call `endCall`. A prewarmed join (`call-prewarm.ts`) that failed is destroyed there and `DirectCallFrame` starts over cold, so it gets this same retry.
- **One Daily instance at a time** — daily-js (strictMode, its default) throws "Duplicate DailyIframe instances are not allowed" from `createCallObject()`/`createFrame()` while any other instance exists, and `destroy()` only deregisters at the very end of an async `leave()`; that race was behind 1:1 "Couldn't join the call" failures. Invariant: **every Daily `destroy()` goes through `trackDailyDestroy`** (`src/lib/call-prewarm.ts`), and **1:1 call code awaits `readyForNewDailyInstance` before `createCallObject()`**: it waits up to 10s for tracked destroys, then (for `DirectCallFrame`'s cold start, via `createCallObjectWhenReady`) evicts any instance still registered (a live-stream preview, a hung teardown) and retries a still-refused create a few times within `CALL_RECONNECT_WINDOW_MS`. A prewarm waits but never evicts (it is speculative and must not tear down something the user is in). Don't set `allowMultipleCallInstances`. Live-stream/Collab/preview frames track their destroys but don't wait before creating yet.
- **Peer loss** — the side still in the room shows "<name>'s connection was lost. Waiting…" and ends the call itself after `CALL_PEER_LOSS_GRACE_MS` (90s). That is deliberately the reconnect window plus a margin: shorten it below the window and the two sides race, one ending the call as the other rejoins. It checks the call row 1s after the peer vanishes and every 5s after, so an ordinary hang-up ends the call before that notice is due.
- **Foreground return** — on `visibilitychange`, a call object found no longer joined goes into the same reconnect, and a camera the OS stopped while backgrounded is turned back on if the user had it on. Audio is never touched on hide. A backgrounded camera is announced to the peer over a Daily app-message (`src/lib/call-camera-pause.ts`, same pattern as `call-hold.ts`) so they see "camera is paused" instead of a frozen frame. Hold and camera-paused are both re-sent, true or false, whenever anyone (re)joins, and cleared locally when the peer leaves — otherwise a side that was out of the room keeps a stale notice.
- **Lifetime** — a 1:1 room and both its tokens live `CALL_ROOM_LIFETIME_SECONDS` (12h, was 1h); `eject_at_room_exp` makes that the cap on one call's length. `createMeetingToken` still defaults to 1h for everything else (live streams, Collab, Circle voice mint a fresh token per join) — a 1:1 call has to pass the long lifetime explicitly because it rejoins with the token it was given at `startCall`.
- **Hang-up delivery** — both `onLeave` closures and `CallButton`'s unmount-mid-ring cancel end the call through `endCallDurably` (`src/lib/end-call-durably.ts`), which is module-level and keeps retrying `endCall` with backoff and on the `online` event for `END_CALL_RETRY_WINDOW_MS` (3 min); any resolved response stops it. Past that the peer's grace period or the cron sweep below closes the row.
- **While a session is up** — `CallSessionProvider` holds a screen wake lock where the API exists, but for a 1:1 call only while this side's camera is on (`sessionNeedsWakeLock`; an audio call has the phone at the user's ear and a WebView has no proximity sensor), and `capacitor-bridge.tsx`'s reset-to-`/home` on resume is skipped (also while an outgoing call is still ringing: `CallButton` owns that ring, and cancels the call if it unmounts mid-ring).

None of this helps a call in a *mobile browser* tab: the browser suspends the page in the background, so that side simply goes quiet until the peer's grace period ends the call. Only the native apps (Android's active-call foreground service, iOS's background audio mode) keep audio running in the background.

Video calls also have a front/back camera flip button (`cycleCamera()`, wired up in both `call-frame.tsx` and the 1:1 `direct-call-frame.tsx`). **Don't gate its visibility on `enumerateDevices()` device-count or `track.getCapabilities().facingMode`** — confirmed live on a real Samsung phone that both are unreliable: some Android camera HALs collapse front+back into a single `videoinput` entry that switches facing mode via constraints instead of exposing two devices, and Android Chrome's `getCapabilities().facingMode` reporting is itself incomplete (a known Chromium/Android gap) — `cycleCamera()` worked fine on that exact hardware while both signals under-reported it, hiding the button entirely. The button is now gated on `Capacitor.isNativePlatform()` instead: this app's real mobile audience is the Capacitor wrapper (see below), where a front+back pair is a given, so there's no "dead click" risk to hide it against. The device-count/capabilities checks are kept only as best-effort fallbacks for a plain browser tab. If you touch this again, test on **real hardware** — a desktop browser's device emulation won't reproduce this (it just proxies the one physical webcam).

**Unanswered calls time out server-side.** The `timeout-missed-calls` cron (`src/app/api/cron/timeout-missed-calls/route.ts`, scheduled every minute by `netlify/functions/timeout-missed-calls.mts` — the route existed long before anything actually ran it) marks a call still `RINGING` 60s after it was placed as `MISSED`, deletes its Daily room, signals both sides and sends the missed-call notification, so an unanswered call ends 60–120s after being placed rather than sitting at `RINGING` forever (which is what used to produce a permanent `already_calling`). A `RINGING` row older than an hour is leftover backlog and is closed silently — no notification, no signal. Because that cron, the caller's `endCall` and the callee's `respondToCall` can all resolve the same ringing call at once, **every transition out of `RINGING` is an `updateMany` guarded on `status: "RINGING"`**, and a 0-count result means someone else already resolved it: skip the side effects (a second missed-call notification, a second room deletion) rather than repeat them. Keep that guard on any new code path that moves a call out of `RINGING`. The same goes for `ACCEPTED`: `endCall`'s hang-up write is guarded on it too, because both clients (and the sweep below) can end one connected call at the same moment.

**The same cron sweeps abandoned `ACCEPTED` rows.** Ending a connected call always needs one of its two clients to still be running and online; when neither is, the row would sit at `ACCEPTED` forever. Any `ACCEPTED` call whose `createdAt` is older than `CALL_ROOM_LIFETIME_SECONDS` — i.e. whose Daily room has expired and ejected everyone — is marked `ENDED`, its room deleted best-effort, both sides signalled and the callee's CallKit report cancelled. The threshold is that shared constant on purpose: anything younger could be a real call still in progress.

**Adding people to a connected call.** A call starts 1:1 and either person can add one of their own connections from the "Add person" button in `GlobalCallFrame`'s Leave/Minimize bar (`add-call-participant-sheet.tsx`); anyone who joined can add more, up to `CALL_MAX_PARTICIPANTS` (8) counting people still being rung. A late "Join" without being rung doesn't exist.

- **Model.** `CallParticipant` (`callId`+`userId` unique; `RINGING`/`JOINED`/`DECLINED`/`MISSED`/`LEFT`; `invitedById`; its own Daily `token`). Rows are lazy: a plain 1:1 call has none and every action takes its old path untouched. The first `inviteToCall` backfills `JOINED` rows for the caller and callee, and from then on the rows — not `callerId`/`calleeId` — say who is in the call. Re-inviting someone who declined, rang out or left reuses their row and resets its `createdAt`, which is what the ring timeout counts from.
- **Actions** (`actions/calls.ts`; shared server rules in `src/lib/call-participants.ts`, used by the cron too). `inviteToCall(callId, inviteeId)`: inviter must be `JOINED` (or a pair member of a call with no rows), call `ACCEPTED`, an accepted connection between inviter and invitee, no block either way between the invitee and *anyone* in the call (answered as a generic `unavailable`, same as an inactive account, so it can't reveal who blocked whom), invitee not already in this call (`already_in_call`) nor ringing/connected on another (`busy`), not `full`. It sends the same web push / FCM `incoming_call` / iOS VoIP payloads as `startCall` with the same `callId` and the inviter's name — so the native ring UI names only the inviter. `getIncomingCall` returns a ringing invite in the same shape as a 1:1 ring (`caller` = inviter, `othersInCall`), but with `calleeToken: null`: the callee-side prewarm would otherwise join the room muted while still ringing, which the people in it would see as someone arriving. `respondToCall` has a participant branch; `getCallStatus` answers per person (a `LEFT`/`DECLINED`/`MISSED` row reads as `ENDED` while the call carries on, which is what makes each client's `isOver` right); `getCallRoster` lists everyone for members only (`useCallRoster`, refreshed on the `call:{userId}` signal and every 10s while someone is ringing).
- **Leaving.** With participant rows, `endCall` means "I leave": a guarded `JOINED → LEFT` for that person, then `settleCall`, which ends the call (row `ENDED`, room deleted, anyone still ringing marked `MISSED` with the usual missed-call notice) only when `shouldEndAfterLeave` says so: nobody `JOINED`, or one person `JOINED` and nobody `RINGING`. So an invite outlives its inviter hanging up as long as one other person is still in the call, and a decline or ring-out that leaves one person alone ends it. Every change to who is in a call starts with `lockConnectedCall` (a no-op `updateMany` guarded on `ACCEPTED`, taken inside the transaction) so invites, answers and the end check run one at a time per call; keep that on any new path. Known gap: a 1:1 hang-up that races the very first invite on that call still ends it for everyone (the hang-up read the call before any rows existed).
- **Cron.** `timeout-missed-calls` also moves a participant `RINGING` longer than `CALL_RING_TIMEOUT_MS` (60s, the same constant the call-level timeout uses) to `MISSED` — notice, cancel push and signal, but the room is left alone — then runs `settleCall`. `sweepStaleAccepted` closes participant rows along with the call.
- **Client.** `DirectCallFrame` takes `remotes[]` from `remotesByUser` (one entry per `user_id`, newest session — `latestJoined` generalised). One remote renders exactly the 1:1 layout; two or more render a grid of tiles with name, avatar fallback and per-person hold/camera-paused state (keyed by the sender's user id from the app-message's `fromId`), one audio element each. The peer-loss grace period and notice don't run while someone this call is ringing hasn't answered (waiting for them isn't a lost connection); the status checks do, and are what end the call if that ring is declined or runs out.
- **Accepted limits.** Daily can't revoke a meeting token, so someone who left (or declined) still holds one that works until the room expires or is deleted; they'd show up in the room without being `JOINED`. A participant whose app dies without a hang-up stays `JOINED` until the call ends. `busy` treats any `RINGING`/`ACCEPTED` call the invitee is in as live, so an abandoned `ACCEPTED` row makes them unaddable until it is swept.

### Analytics: PostHog (session replay + product analytics)

`src/lib/posthog-client.ts` (init/identify/reset) + `src/components/posthog-provider.tsx` (mounted once, unconditionally, in `layout.tsx`) — replaced Microsoft Clarity (2026-09) rather than running both, since two session-replay tools recording the same sessions doubled the client-side recording overhead and the privacy-disclosure surface for no real benefit. Opt-in until both `NEXT_PUBLIC_POSTHOG_KEY`/`NEXT_PUBLIC_POSTHOG_HOST` are set (same "inert until configured" pattern as GTM elsewhere), and session replay itself additionally needs "Record user sessions" turned on in the PostHog project's own dashboard settings — code alone can't reach that toggle. `src/proxy.ts`'s CSP `connect-src` opens PostHog's ingest host only once configured. **No IP-derived location:** `before_send: disablePostHogGeoIp` (`src/lib/posthog-geoip.ts`) stamps `$geoip_disable: true` on every event (replay `$snapshot` included) so PostHog skips GeoIP enrichment, which is what lets the store privacy labels say no approximate/coarse location. posthog-js's `ip` init option is a documented no-op in the installed version, so the PostHog project's "Discard client IP data" setting is the dashboard-side half; keep both if you touch this.

**Privacy**: this app has a real end-to-end-encrypted secret chat feature (`src/lib/e2ee/`) whose entire point is that not even YuKon3t's own servers can read the plaintext — a third-party screen recorder capturing that same text as rendered pixels would quietly undermine that guarantee regardless of the encryption itself. Every message bubble in `chat-thread.tsx` (secret or not — an ordinary DM is still private content too) carries a `ph-no-capture` class, which `posthog-client.ts`'s `session_recording.blockClass` config turns into an actual recording exclusion (rendered as a placeholder box in the replay), not just an autocapture-events exclusion. If you add another surface that shows private user content (a new kind of private form, a payment field, etc.), give it the same class — it's not automatic.

**A secret chat that is on must look like any other chat.** Nothing a bystander can see may mark it: no label, lock or accent strip in the thread, `inboxPreview` returns a plain "Message", `pushPreview` a plain "New message" (`src/lib/e2ee/secret-chat.ts`), the bubble placeholders in `use-secret-chat.ts` are "…" / "Message unavailable on this device", and user-facing errors don't say "secret" or "encrypt". All controls (turn on, verify code, turn off, unlock/reset) are in the "Chat privacy" sheet, opened from the ⋯ menu in the 1:1 header (`chat-options-menu.tsx`; the sheet itself is rendered by `secret-chat-bar.tsx`, connected through `ChatOptionsProvider`). That menu is on every 1:1 chat and identical in every state — never add an item, label or badge that depends on the chat being secret, and never bring back an opt-in strip on ordinary chats (its absence would be the tell). `SecretChatBar` shows a strip only when the user must act or is at risk: the peer asked to turn it on, my own request is pending (messages are not encrypted yet — this is also what appears the moment the peer turns it off), this device needs the passphrase ("Unlock messages"), or the peer's key changed. The recovery passphrase inputs show their characters by default (`PasswordInput` with `defaultVisible`) and are `ph-no-capture`. Still distinguishable, by design or necessity: the inbox shows "Message" instead of real text, the first paint of a message shows "…" briefly, and corrections aren't offered.

`resetPostHog()` runs in `nav.tsx`'s `handleSignOut`, same reasoning as that function's existing FCM-token/draft-storage cleanup: a shared/public device's next signed-in session shouldn't inherit the previous account's identity in PostHog's records.

### Review-prompt gate ("How's the yukon3t app?")

`src/components/review-prompt-gate.tsx` (mounted once in `layout.tsx`, native-app-only — `Capacitor.isNativePlatform()`) shows a custom feedback modal *before* ever reaching the OS's native store-review popup, specifically so a lukewarm/negative signal can never turn into a public bad review: "I love it" is the only choice that calls `requestNativeReview()` (`src/lib/in-app-review.ts`, wrapping `@capacitor-community/in-app-review`'s Play Core / `SKStoreReviewController` bridge) and sets `User.reviewPromptStatus` to the terminal `LOVED`; "Could be better" instead routes to a private free-text form (`AppFeedback`, visible only at `/admin/feedback`, with an `APP_FEEDBACK_SUBMITTED` notification to every admin) and sets the terminal `DECLINED`; "Maybe later" just snoozes (`reviewPromptAskCount`/`LastAskedAt`, both PENDING-only fields — see the actual thresholds in `src/lib/review-prompt.ts`: minimum account age, at least one real action taken (a post, a message, or a Circle join), a 14-day snooze, capped at 3 total asks before giving up for good). Like every other Capacitor plugin newly added to `package.json`, `@capacitor-community/in-app-review` needs `npx cap sync android` / `npm run cap:sync:ios` before the native popup actually works on a real device — until then `requestNativeReview()` fails closed (caught, logged, never crashes) rather than showing anything.

### App update prompts (native app, web-delivered)

`src/components/app-update-gate.tsx` (mounted once in `layout.tsx` for everyone, native-only via `Capacitor.isNativePlatform()`) reads `App.getInfo()` at launch and on foreground and asks the public `GET /api/app-version?p=android|ios&b=<build>&v=<version>` (at most every 6h per build, every foreground while blocked). Rules are the pure `src/lib/app-version.ts` (`decideUpdateStatus`, version compare, sanitizing, `olderBuildTokenWhere`); policy is one `AppVersionPolicy` row per platform, edited on `/admin/system` (`actions/app-version.ts`, audit-logged). **Nothing prompts until the owner enables a platform and sets `latestBuild`**: no row, `enabled = false`, no `latestBuild` (`latestVersion` and iOS auto-detect only add to it) or an unknown build all answer `current`, and so does any prompt with no store link to open. `soft` = dismissible banner (3-day snooze per build and target); iOS can also go `soft` from the App Store's live version (`iosAutoDetect`, cached iTunes lookup in `app-version-server.ts`). **Force is owner-only, via `minBuild`** (typed confirmation; must be at or below `latestBuild`) — never from a missing plugin, attestation state or anything automatic; the block screen keeps Update, Help/FAQ (it steps aside on `/faq` and `/legal`) and Sign out reachable. `FcmToken.platform/build/appVersion` are filled when the app registers its token, for the admin build breakdown and the manual, confirmed, 1/hour-per-platform "Notify users on older builds" push (`sendFcmNoticeToTokens`). **Operating it:** once a Play/App Store rollout reaches 100%, set that platform's `latestBuild` to the new build number. The Play In-App Updates plugin is deliberately deferred to the next native release; until then the Update button opens the store listing. Separate from `StaleBuildReload` (stale web bundle) and from attestation enforcement.

### Domain model (see `prisma/schema.prisma`)

- **Circles** (communities) → **Channels** → `ChannelVoiceParticipant` for live voice. A PRIVATE Circle's owner or co-admin (`MODERATOR` membership; not `isCircleAdmin`, no site-admin shortcut) can invite their own accepted connections (`inviteToCircle`, max 50 per request, own `circleInvite` limiter 10/h) as `CircleInvite` rows (PENDING/ACCEPTED/DECLINED, no expiry, an admin can cancel a pending one); eligibility and the re-invite rules (DECLINED, or ACCEPTED but no longer a member, reset to PENDING) are in the pure `src/lib/circle-invite.ts`. **An invite is only acceptable while its inviter can still invite** (`canInviterStillInvite`: owner, or still a MODERATOR member, account ACTIVE); otherwise accepting refuses with `invite_expired` and deletes the row, and the invitee is never shown it (`loadStandingCircleInvites`). The admins' Invited list marks such a PENDING invite `stale` (`isStaleCircleInvite`, loaded by `loadCircleInvitesForAdmins`, which selects only the inviter fields the check needs and drops them) with a "can no longer be accepted" label, still cancellable; re-inviting that person resets the same row to PENDING from the current inviter and notifies again, like a DECLINED one. Resets and the accept/delete claims are guarded on both status and `inviterId`. Inviting someone with a PENDING join request approves it instead. `respondToCircleInvite` (invitee only, guarded PENDING claim, blocks re-checked with inviter and owner) adds a MEMBER and notifies the inviter (`CIRCLE_INVITE_ACCEPTED`) and the other admins (`CIRCLE_JOINED`), never subscribers; `joinCircle` on a private Circle accepts a pending invite. `CIRCLE_INVITE` is bell + FCM push. Going PUBLIC deletes pending invites. `createCircle` is idempotent against a double-submit: the same creator, name (case-insensitive) and parent within 2 minutes resolves to the Circle already made (checked before the rate limiter and again under a `pg_advisory_xact_lock` in the creating transaction, rules in the pure `src/lib/circle-create-dedupe.ts`) with no repeat notifications, and the wizard's final button disables itself while pending.
- **Private Circles don't exist for non-members** (pure rules + Prisma fragments in `src/lib/circle-visibility.ts`, unit-tested; `src/lib/circle-visibility-exposure.test.ts` scans the source). A PRIVATE Circle/sub-circle is seen by its members only: not listed (`/circles`, search incl. the embedding search, sub-circle lists, `getMyCircles`' parent names), `/circles/[slug]` is `notFound()` (site admins included; they have `/admin/circles`, which lists it unlinked), and nothing inside it reaches anyone else. The one exception is a standing `CircleInvite` (`loadStandingCircleInvites`): header + Accept/Decline only (`canSeeCircle` vs `canSeeCircleContent`). It is **invite-only**: `joinCircle` accepts a pending invite or answers `not_found`; no `CircleJoinRequest` is created any more (old PENDING rows stay, admins can still answer them, the requester no longer sees the Circle). Every new Circle list must use `visibleCircleWhere`; `isCircleAdmin`'s site-admin shortcut must never open a PRIVATE Circle's content (gate on `canSeeCircleContent` first, as the page, `getCirclePollAccess`, `circleEventsScope` and `loadMoreCirclePosts` do). Posts: `buildVisiblePostsWhere` (inside `getVisiblePostsWhere`) reaches a PRIVATE Circle's posts through current membership only, the author's own included once they leave, and drops a repost/share whose original is in a PRIVATE Circle the viewer isn't in (so going private hides old reposts too). Notifications: `/notifications` and `/api/badge-counts` add `circleNotificationVisibleWhere` (read-time, nothing deleted; keeps a row about the Circle while an invite is pending, and admins' `CIRCLE_CREATED`, which opens `/admin/circles` for a private one). Fan-outs keyed on RSVPs/claims/authors (event reminders/changes, `POLL_SCHEDULED`, like/comment/RSVP notices) go through `filterCircleContentViewers`; a PRIVATE Circle's creation and RSVPs are never announced to subscribers. Not covered: copies made while it was public (a Story/Muse share keeps its copied media; its link 404s), pushes already delivered, and site-admin moderation views (`/post/[id]`, live streams, admin pages).
- **Posts/Comments/Likes/Stories** — standard social graph. A multi-photo post is *not* one Post row with several `mediaUrls` — each photo is its own Post row (one `mediaUrls` entry each), sharing a `Post.albumId` and ordered by `albumIndex`; only `albumIndex 0` (the "lead", which also carries the caption) is ever surfaced by a feed/search/profile listing (`LEAD_POST_ONLY` in `src/lib/post-visibility.ts`) — the rest are reached via that lead's own carousel (`PostCard`'s `AlbumCarousel`) and are each independently likeable/commentable/repostable/shareable through their own `/post/[id]`. Deleting any post in an album deletes the whole album together (`deletePost` in `actions/posts.ts`); partial-album deletion isn't supported. Any new query that lists posts (not a single-post lookup) needs to apply `LEAD_POST_ONLY` too, or a multi-photo post's siblings will double-render as separate feed entries.
- **Collab** — `CollabBoardPost`/`CollabParticipant`/`CollabSessionParticipant`, a separate live-collaboration feature from Circles/posts A PRIVATE collab's admin can also invite whole Circles they *created* (owner-only, `Circle.createdById`; not `isCircleAdmin`, whose site-admin shortcut would open anyone's Circle): `inviteToCollab`/`createCollabPost` take `circleIds` (max 5) and copy the Circle's current members into ordinary PENDING `CollabInvite` rows (no live link; each member still accepts). Exclusions, dedupe and the 200-new-invite cap (`too_large`, never a subset) live in the pure `src/lib/collab-circle-invite.ts` (`selectCircleInvitees`): inviter, participants, anyone with an existing invite except a stale PENDING one (a DECLINED one isn't re-sent by a bulk invite; a stale one is reset to PENDING from the current inviter and counts toward the 200 cap like a new invite), blocked either way, the inviter's hidden-chat peers, non-`ACTIVE` accounts; Circle members needn't be connections. Own `collabCircleInvite` limiter (5/h); notifications stay bell-only `COLLAB_INVITE`. **A `CollabInvite` only stands while its inviter can still invite** (`canCollabInviterStillInvite` in the pure `src/lib/collab-invite.ts`, sharing `src/lib/invite-standing.ts` with Circles: the collab's author, or an OWNER/MODERATOR participant, account ACTIVE). Inviting and cancelling are gated on the same rule (`canInviteToCollab`, no site-admin shortcut, so no invite is born unacceptable). `respondToCollabInvite` (invitee only) refuses a stale invite with `invite_expired` and deletes it with the invitee's bell entry, like Circles; the invitee never sees one (`loadStandingCollabInvite`, which also means it no longer grants view access). Accept and decline are guarded claims (`pendingInviteClaimWhere`: `updateMany` on id, invitee, `PENDING` and the `inviterId` judged); a 0 count answers `not_found` with no side effects, so a double accept, or an accept after a cancel/decline/re-send, adds no participant twice and notifies nobody twice. The admins' Invited list (`loadCollabInvitesForAdmins`, inviter fields dropped) labels a stale PENDING invite "can no longer be accepted"; `cancelCollabInvite` deletes any PENDING one. Re-inviting (`planCollabInvites` in `sendCollabInvites`, so also the start-session sheet): a DECLINED (individual only) or stale PENDING row is reset to PENDING from the current inviter (guarded on the status and `inviterId` read) and notified again; the pickers offer a stale invitee again (`collabInviteExcludesInvitee`). Nothing records that an invite came from a Circle, so the page's Invited list (`splitVisibleInvites`) names an invitee only to the admin who sent it, if accepted, or if the viewer is connected to / shares a Circle with them; the rest are only counted. **Start session** (`startCollabSession`, `actions/collab-session.ts`): on a PRIVATE collab an OWNER/MODERATOR's "Start session" (nobody in yet) opens a sheet in `collab-session-room.tsx` (notify toggle, default on; optional connections/owned-Circles pickers) instead of joining at once; PUBLIC collabs and non-moderators are unchanged. Invites go through the same `sendCollabInvites` (`src/lib/collab-invites-server.ts`, shared with `inviteToCollab`/`createCollabPost`, kept out of the `use server` file); any invite error returns before the join, so nothing starts and nobody is notified. After a successful join, `COLLAB_SESSION_STARTED` (bell + FCM) goes to every participant but the starter, at most once per collab per 30 min: no table, the newest such row for the collab (found via the recipients' `recipientId, createdAt` index) is the cooldown clock, checked and written in one transaction that row-locks the collab first. Pure rules in `src/lib/collab-session-start.ts`.
- **Polls** (`Poll`/`PollOption`/`PollVote`, migration `20261019120000_polls`) in a Circle (optionally one channel) or on a collab, exactly one parent (`pollParentError` + DB CHECK constraints). Rules are the pure, tested `src/lib/polls.ts`; access and the browser view (`PollView`: counts only, never who voted, admins included) are `src/lib/polls-data.ts`; actions `actions/polls.ts` (`pollCreate`/`pollManage`/`pollVote` limiters). Create: the parent's creator or a co-admin (OWNER/MODERATOR) only, still a member, no site-admin shortcut; plain members can't. Vote: members / participants (a PRIVATE channel's poll: its allow-list or an admin); a PRIVATE Circle's or collab's polls are invisible to outsiders (an invitee too). Manage (edit, close/reopen, delete): poll creator while a member, or `isCircleAdmin`/`isCollabAdmin`. Kind (GENERAL/SCHEDULE) and single/multiple choice are fixed at creation; an edited or removed option loses its votes (`planPollOptionEdits`), and `updatePoll` answers `confirm_clear` until the editor confirms. Text goes through `moderateText` and is refused if flagged. SCHEDULE options are absolute instants entered/shown in UTC (local time alongside). "Schedule" (admin any time, creator once closed; once per poll, from a leading option, closes the poll): in a Circle it creates an event `Post` (`eventAt`, so RSVPs and the event-reminders cron apply) in the poll's text channel or `general`, linked as `Poll.scheduledPostId`; that post then runs through `afterPostCreated` (`src/lib/post-created.ts`, shared with `createPost`: feed category + embedding via `classifyPostCategory` before the transaction, activity/analytics, `notifySubscribers` or `notifyConnections` and the Home feed signal, members-only Circles/channels skipped; that fan-out is synchronous, as for any post). On a collab it adds a `CollabOneOffSession` row (migration `20261019140000_collab_one_off_sessions`, which replaced the old single `CollabBoardPost.oneOffSessionAt`/`oneOffReminderSentAt` columns; several per collab, `pollId` unique and set null if the poll is deleted), separate from `nextSessionAt` (which the cron rolls forward and `updateCollabPost` recomputes). `collab-session-reminders` claims each due row on its own `reminderSentAt` and skips sending when the same collab+instant (`sessionOccurrenceKey`) was already reminded in that run; the collab page lists the upcoming ones (participants/owner only) and each has `/api/collab/[id]/calendar?session=<rowId>` (404 unless that row is this collab's and still ahead). Notifications: `POLL_CREATED` bell-only to up to 500 members/participants on creation (never on edit); `POLL_SCHEDULED` bell + FCM to everyone who voted. Blocked-either-way users are skipped. Notification links (`notificationHref`, and the `POLL_SCHEDULED` push URL) land on `/circles/<slug>#polls` or `/collab/<id>#polls`; `PollSection` is the `#polls` anchor (cards are `#poll-<id>`) and re-scrolls on mount (`pollScrollTarget`); `markReadByTarget` compares hrefs without the fragment. **Live:** every poll mutation (create, edit, close/reopen, delete, vote, schedule) publishes an empty `changed` signal on `REALTIME_CHANNELS.circlePolls` / `collabPolls`; each open `PollSection` coalesces it with `createSignalThrottle` (random 0-2s, at most one refetch per 5s: `POLL_SIGNAL_*`) and re-reads everything it has loaded through `loadPolls` (mode `through`, capped at `POLLS_REFRESH_MAX`); the voter still gets fresh counts straight from `votePoll`, and unsubmitted picks survive a refresh. **Pagination:** first `POLLS_PAGE_SIZE` (30) server-rendered, then "Load more" = `loadPolls` mode `older` with a `(createdAt, id)` cursor (`pollListSchema`, `pollList` limiter 120/min), visibility from `circlePollScope`/`collabPollScope` (`circlePollWhere` is shared with the Circle page).
- **Circle events** (event `Post`s with `eventAt` in a Circle; migration `20261021120000_circle_events`). Pure rules in `src/lib/circle-events.ts` (organizer = the author while a member, or the Circle's owner/co-admin by role, no site-admin shortcut; bring-list limits; nudge cooldown/recipients) and `src/lib/event-recurrence.ts` (UTC date maths), server half `src/lib/circle-events-data.ts`, actions `actions/circle-events.ts` (limiters `eventOrganize`, `eventBringClaim`, `eventNudge`, `circleEventList`). **Coming up** (`CircleEventsSection`, the Circle page's `#events` anchor): upcoming lead event posts in the channels the viewer can open, AND `getVisiblePostsWhere` (blocks, HIDDEN, inactive authors), soonest first, 20 per page, one-tap Going / Maybe through `setRsvp` (see the organizer-tools bullet). **Calendar**: `/api/events/[id]/calendar` (.ics, 401 signed out, 404 unless `loadCircleEventAccess` allows it and it hasn't started); no subscribable per-Circle feed (it would need a secret token). **Bring list** (`EventBringItem`, cascade with the post): organizer adds (max 20, counted under a `FOR UPDATE` on the post), edits, removes, unassigns; a member who can see the event claims with an `updateMany` guarded on `claimedById: null` (0 = `taken`); text through `moderateText`; a blocked-either-way claimer shows as "someone". **Nudge** (`nudgeEventNonResponders`): organizer, future events only, `EVENT_RSVP_NUDGE` bell + FCM to ACTIVE members who can open the channel, minus RSVPs, author, sender and anyone blocked with either, max 500; `Post.eventNudgedAt` is claimed (guarded `updateMany`, 12h) before sending, and nothing is claimed when nobody is left. **Repeat** (`EventSeries`, `Post.eventSeriesId`/`eventSeriesIndex` unique): chosen in the composer for a Circle event only (weekly / every 2 weeks / monthly on the same day, last day in shorter months; 2-12 dates or an end date within a year); each date is its own post. The `event-series` cron (every 15 min, `netlify/functions/event-series.mts`) posts the next date 1h after the latest starts, copying text/location/channel/category and the embedding, with **no** `afterPostCreated` fan-out (no subscriber/connection notifications, no Home signal); claimed via `updateMany` on `lastIndex` + the unique pair; ends the series when it's over, the author is no longer an ACTIVE member who can post there, or any occurrence was moderated. Organizers can stop it (`stopEventSeries`). The poll-schedule path doesn't offer repeat. The organizer panel (calendar, repeat, nudge, bring list, reschedule/cancel) is `CircleEventPanel`, under the post on `/post/[id]` and lazily loaded by "Details, bring list and calendar" on the event card everywhere else (`CircleEventDetails` -> `loadCircleEventDetails`; this was the only way to reach the bring list from a Circle, which the owner couldn't find); "Coming up" is a compact agenda (title, time, going count, RSVP, Details link to the post), and its RSVP and the card's are kept in step by `src/lib/rsvp-sync.ts` (same-tab CustomEvent). **Cancel / reschedule** (migration `20261021180000_circle_event_cancel_reschedule`; `cancelCircleEvent` / `rescheduleCircleEvent`, organizer only, before the start, `eventOrganize` limiter, optional reason <= 280 chars through `moderateText`): `Post.eventCancelledAt`/`eventCancelReason`, `eventRescheduledAt`/`eventRescheduleReason`/`eventPreviousAt`. Both are guarded `updateMany` claims (cancel: not cancelled and not started; reschedule: on the `eventAt` read, not cancelled) and notify `EVENT_CANCELLED`/`EVENT_RESCHEDULED` (bell + FCM, `eventChangePushBody` with the new time in UTC and the reason) to `eventChangeRecipients`: author + RSVPs + bring-list claimers, minus the actor and anyone blocked either way with them, ACTIVE only, max 500. ### Dual deployment: Vercel + Netlify, different mechanisms

Both are live off this repo, same Neon database. **Netlify auto-deploys on `git push` to `master`.** Vercel does **not** auto-deploy from this repo config — it needs an explicit `vercel --prod`. A change isn't "live everywhere" until both have happened. Env vars must be set separately on each platform (`vercel env add` / `netlify env:set`) — a var only present in local `.env` silently leaks into a Vercel build (Next's own env loading finds it) but is simply absent on Netlify. See `SECURITY.md` for the full incident history on this, including a Windows-specific `netlify deploy --prod` bundling bug (use git-push/build-hook deploys instead of the local CLI on Windows) and a GitHub-cross-account webhook mixup.

Both platforms' production builds run `scripts/migrate-if-production.sh` before `next build` (wired into `package.json`'s `build` script for Vercel, and directly into `netlify.toml`'s `command` for Netlify, since Netlify's build bypasses `package.json`'s `build` script entirely). That script runs `prisma migrate deploy` only when `VERCEL_ENV`/`CONTEXT` is `production` — a preview/branch build or local `npm run build` skips it, so an unmerged migration never touches the shared prod database early. Before this existed, a schema migration applied to local dev only (via `npm run db:migrate`) would deploy code that silently 500'd in production until someone applied the migration to Neon by hand — if you ever bypass this script (e.g. deploying a prebuilt artifact), apply the migration to production yourself first.

`SECURITY.md` also documents the full list of implemented security controls (CSP nonce, rate limiting via Upstash, SSRF-guarded remote image fetch, etc.) and known accepted gaps — read it before changing anything auth/upload/moderation-adjacent.

**Rate limiting** (`src/lib/rate-limit.ts`): every limiter counts in its own Redis key space, `rl:<name>` after its key in `limiterDefinitions` (the few that already passed an explicit prefix, e.g. `subCircleCreate`, keep it so their counters didn't reset). Before this they all shared Upstash's default prefix, so two limiters with the same identifier and window length counted against one counter — viewing Muse videos used up the message-send budget. A check times out after 1s rather than the library's 5s, and both a timeout and an outright Upstash error **fail open** (the request is allowed) with a `[rate-limit]` log line — a slow or down Redis degrades to unlimited, never to an outage, so those log lines are the only trace that limits stopped enforcing. Those reports are throttled to one per 10 minutes per server instance per failure kind (thrown error vs. timeout), with the number suppressed in between attached to the Sentry event, because `src/proxy.ts` runs a check on nearly every request and an exhausted Upstash plan would otherwise send one Sentry event per request. Every proxy check also costs an Upstash command, so `/api/cron/*` (bearer-authenticated), `/api/health`, `/api/build-id` and the static `/sw.js`, `/offline.html`, `/manifest.webmanifest`, `/robots.txt` and `/sitemap.xml` skip the `pageRequest` limiter (`PAGE_LIMIT_EXEMPT_*` in the proxy); everything else, including every other `/api` route, auth callbacks and Server Actions, stays limited. **The page limit is three buckets, not one** (`pageLimitChecks` in `src/lib/page-rate-limit.ts`, sizes in `rate-limit.ts`): a request carrying the device-id cookie counts against `pageRequestDevice` (per device) and `pageRequestNetwork` (per client IP, a high ceiling for shared Wi-Fi and carrier CGNAT), so it costs two Upstash commands; one without the cookie counts against the strict per-IP `pageRequest`; one with no client address isn't counted. The client IP comes from `clientIpFromHeaders` (Netlify's `x-nf-client-connection-ip` first, which a client can't set), shared with `src/lib/client-ip.ts`. A single 300-a-minute per-IP bucket refused two phones on one Wi-Fi mid-call on 2026-10-14 and left the app on a bare text page: a refused page load now gets a small self-reloading page in the reader's language (`rateLimitPage`), anything else a bare 429, both with `Retry-After`.

### Realtime layer (Supabase Realtime Broadcast) — replaced all polling (2026-09-16)

Every "live" UI in this app — nav badges, chat/messages, calls, live streams, Circle voice channels, Collab sessions, the Home feed — used to work by polling a Server Action/API route on an interval (`usePolling`, `src/lib/use-polling.ts`, since deleted). All of it now runs on Supabase Realtime Broadcast instead: `src/lib/realtime-server.ts` (`publishEvent`, server-only) and `src/lib/realtime-client.ts` (`useRealtimeEvent`, the client hook), with every channel name centralized in `src/lib/realtime-channels.ts` (`REALTIME_CHANNELS`).

**Design — broadcasts are thin signals, never the payload itself.** This app's authorization lives entirely in Server Actions/API routes (see "Server Actions are the primary write path" above); Supabase Realtime's own access control (private channels + RLS) is built around Supabase Auth, which this app doesn't use. Rather than bridging two auth systems, every channel is a **public** broadcast carrying only "something changed, go refetch" (e.g. `{ conversationId }`, never message content) — the client's existing, already-authorized fetch is what returns the real data, exactly as it did on a poll tick. A channel name leaking is not a security issue: at most it tells an eavesdropper "activity happened," never what that activity was. Only Supabase's Realtime service is used — the actual data stays on Neon, and Supabase's own Postgres/Auth are untouched.

`useRealtimeEvent(channel, event, handler)` also refetches once on tab-focus-regain as a safety net against a signal missed while the WebSocket was disconnected (backgrounded mobile WebView, a brief network drop) — a one-shot check, not a timer. That resync is shared across every instance of the hook (`createResyncScheduler` in `realtime-client.ts`), not run per instance: one `visibilitychange` listener runs each distinct handler once (a function passed to several instances — e.g. one refetch on two channels — is deduped), spread over a random 0–2s, and never the same handler twice within 10s (a too-recent one is deferred to the end of that window, not dropped). Before this, foregrounding the app on Home fired ~10 requests in the same tick. **Calls opt out of the delay**: pass `{ resync: "immediate" }` as the 4th argument (used by `incoming-call-listener.tsx`'s two checks and `call-button.tsx`'s caller-side status check) and that handler resyncs the instant the tab is visible, on every foreground, ignoring the 10s window — someone opening the app mid-ring must see the banner now, and one extra request is the cheaper mistake. Don't reach for it for anything that isn't that latency-critical; it's exactly the thundering herd the scheduler exists to prevent.

**One Supabase channel per topic, reference-counted** (`createChannelRegistry`). `RealtimeClient.channel(topic)` returns the *existing* channel object for a topic that's already open, and `removeChannel()` leaves that one shared channel outright — so when each hook instance opened and removed "its own" channel, the first of two components on a topic to unmount (`CallButton` and `IncomingCallListener` on `call:{userId}`; the three Home components on `live-streams`) silently unsubscribed the other until the next full reload. Every subscriber now goes through the registry, which joins on the first listener and leaves only after the last one goes (deferred a microtask, so a same-commit handoff doesn't leave + rejoin, and a re-request during a still-pending leave waits for it to finish). Never call `supabase.channel()`/`removeChannel()` directly from a component.

**Channels everyone hears at once are throttled on the client, not just subscribed to.** A `home-feed:*` signal fires for every public post by anyone and reaches every open Home tab in the same instant, so `post-feed-section.tsx` coalesces them (`createSignalThrottle`): each tab waits a random 0–5s before fetching and makes at most one signal-driven fetch per 20s however many posts land in between. Two cases bypass it and fetch right away — the focus resync, and any signal that arrives while the viewer's own post is still sending (it's most likely the one announcing it). Live-stream signals carry a `kind` (`comment`/`presence`/`stage`, see `src/lib/live-stream-signal.ts`) so a listener refetches only what that kind is about instead of everything — `presence` (viewer counts) is additionally throttled to one refetch per 5s; a missing or unknown kind (the focus resync's null payload, a server still on pre-`kind` code mid-deploy, a kind this client's cached JS doesn't know yet) falls back to a full refetch, so adding a kind is safe to deploy in either order. The kind is the *whole* payload — still never data. The global `announcements` signal just sets the what's-new badge locally (`use-nav-badges.ts`) rather than sending every signed-in client to `/api/badge-counts` at once.

On the server, `publishEvent` has a 2s timeout (it's awaited inside nearly every mutation — a hung Supabase call must not hang the write), and `publishEvents` sends a fan-out as one batched request per 100 events instead of one HTTP call per recipient (see `afterMessageSent` in `actions/messages.ts`). Both stay best-effort and never throw.

**Not migrated, deliberately**: `recordLiveStreamHeartbeat` (a periodic "I'm still here" keepalive the `end-inactive-streams` cron watches for, not an event-driven concern) keeps its own timer, as does anything else that's fundamentally "prove liveness on a schedule" rather than "refetch when something changed."

Setup: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (client-safe), `SUPABASE_SECRET_KEY` (server-only) — see `.env.example`. No SQL/RLS/table setup needed in the Supabase project at all, since it's used purely as a signaling relay.

### Automated database backups

A daily encrypted logical backup of every table runs via the `backup-database` cron (`src/lib/db-backup.ts`), same Netlify Scheduled Function pattern as every other cron. It uploads to a **separate, private** R2 bucket (`BACKUP_R2_BUCKET_NAME`) — never the public media bucket (`R2_BUCKET_NAME`), which serves every object under it to anyone via `R2_PUBLIC_URL`. The cron no-ops (503) until `BACKUP_R2_BUCKET_NAME`/`BACKUP_ENCRYPTION_KEY` are actually configured; see `SECURITY.md`'s "Automated database backups" section for the full threat model and one-time setup steps. Restore is manual and deliberate only: `npm run db:restore-backup` (`scripts/restore-database-backup.ts`), never automatic.

### Scalability pass (2026-09-14)

A concurrent-user-focused audit (not a security one) found and fixed the real bottlenecks, in priority order:

- **Nav badge polling consolidated 4→1.** Messages/connections/notifications/announcements unread-counts used to be 4 independent `usePolling` loops (`src/components/nav.tsx`, `notification-bell.tsx`, `whats-new-bell.tsx`), each re-running `requireUser()`'s own DB lookup, all mounted for every signed-in user on every page. Now one `/api/badge-counts` route (`requireUser()` once, 4 count queries in `Promise.all`) backs one shared `useNavBadges` fetch (`src/lib/use-nav-badges.ts`); `NotificationBell`/`WhatsNewBell` are now presentational, taking `count`/`unread` as props instead of self-fetching. `post-feed-section.tsx`/`live-stream-strip.tsx`/`incoming-call-listener.tsx` were at the time deliberately left as their own separate polls — each already just one poller with genuinely different data/latency needs (incoming-call in particular was latency-critical at 5s) — but as of the 2026-09-16 realtime migration (see "Realtime layer" above), none of these poll at all anymore; every one of them, plus everything else in this list, moved to Supabase Realtime.
- **Unbounded reaction/comment/story-viewer queries fixed.** `toggleLike`/`toggleCommentReaction` used to ship one row per reactor on every single like/react click — a viral post's full reactor list re-downloaded by every subsequent click. Now aggregated in Postgres via `groupBy` (`emoji`, `_count`) instead, returning `{emoji, count, reactedByMe}[]` (`src/lib/reactions.ts`) — correct at any scale, not just capped. `getPostComments`/the standalone `/post/[id]` page share one helper now (`src/lib/comments-data.ts`) that also batches this aggregation across every comment on the post in one query, and caps comment load at 500 (oldest-first — safe, since a reply's parent always precedes it, so `buildCommentTree` never orphans one). `getStoryViewers` similarly capped at 200. Message reactions were deliberately left untouched — at the time a conversation was always exactly 2 people, so a message could never have more than 2 reactions. That premise is stale now that group chats exist (see "Domain model"): a message's raw reaction rows are bounded by the group's member count, not by 2. `ReactionBar` (shared by posts/comments/messages) now renders pre-aggregated summaries; `chat-thread.tsx` adapts its still-raw message reactions via `summarizeReactionRows` at render time rather than duplicating the DB-side aggregation for a case that doesn't need it.
- **Open question, unverified**: whether production `DATABASE_URL` (Vercel/Netlify) actually uses Neon's pooled (`-pooler`) endpoint rather than a direct connection. `src/lib/prisma.ts`'s own comment already flags this as what actually caps concurrent capacity in a serverless deployment — each function instance gets its own small connection pool (`max` defaults to 5), and without a real pooler in front, enough concurrent instances will exhaust Postgres's own connection limit regardless of how small each instance's pool is. Check both platforms' `DATABASE_URL` against Neon's dashboard connection string (the pooled one has `-pooler` in the hostname) before assuming this is handled.

**Second pass (2026-10-10)** — aimed at what happens when many clients react to the same thing at the same moment, plus two things that had silently stopped working. Each is documented where it lives rather than repeated here:

- Realtime: shared reference-counted channels (a real cross-component unsubscribe bug), shared/deduped/jittered foreground resync with an immediate option for calls, coalesced `home-feed` signals, `kind`-scoped live-stream signals, batched `publishEvents`, a 2s `publishEvent` timeout — see "Realtime layer".
- Search: the pgvector HNSW indexes two Prisma-generated migrations had dropped are back, with a guard against it happening again — see "pgvector HNSW indexes".
- Rate limiting: per-limiter Redis prefixes, 1s timeout, fail-open with logging — see the "Rate limiting" paragraph under "Dual deployment".
- Calls: `timeout-missed-calls` is actually scheduled now, and every transition out of `RINGING` is guarded — see "Calls". 1:1 calls also reconnect instead of ending on a dropped connection, and stale `ACCEPTED` rows are swept.

**Known open items, not yet addressed**: production `DATABASE_URL` using Neon's pooler is still unverified (the bullet above); media is served straight from the R2 public URL with no cache headers or CDN in front (verify what `R2_PUBLIC_URL` actually points at); the video crons declare `maxDuration = 300`, an assumption that hasn't been checked against Netlify's own function limits; announcement broadcast and subscriber-notification fan-out (`notifySubscribers`) still run synchronously inside the request that triggers them; search's exact-match path is unindexed `ILIKE`; nothing ever prunes `Notification` or `AnalyticsEvent` rows; and the database backup builds the whole dump in memory before uploading.
