## Agent delegation policy

Never do the work yourself directly — always hand every task off to a sub-agent (the `Agent` tool) rather than using your own tools inline. Route by difficulty:

- **Simple/routine tasks** (small edits, verification runs, straightforward fixes): delegate to a Sonnet or Haiku sub-agent.
- **Hard/reasoning-heavy tasks** (architecture decisions, tricky bugs, anything needing careful multi-step thinking): delegate to an Opus sub-agent — the `model` option accepts `"opus"`, which resolves to the current flagship Opus build available to the tool (there is no separately-selectable "Opus 5.5"; ignore that specific name if it's ever requested and use `"opus"`).

### Mobile (Capacitor — Android/iOS wrapper)

```bash
npx cap sync android     # after changing native plugins/capacitor.config.ts
npm run cap:sync:ios     # same, for iOS — NOT plain `npx cap sync ios`, see below
cd android && ./gradlew assembleDebug    # debug APK for sideloading/testing
cd android && ./gradlew bundleRelease    # signed AAB for Play Store (needs android/keystore.properties, gitignored)
```

**Native plugin patches**: `patch-package` (`postinstall` script) reapplies anything in `patches/` after every `npm install` — durable across reinstalls/CI, unlike hand-editing `node_modules` directly. Currently patches `@capacitor/share`'s Android plugin (`patches/@capacitor+share+8.0.1.patch`): its `isPresenting` flag only ever clears when the share sheet's own activity-result callback fires, which doesn't always happen if a share gets abandoned mid-flow (backgrounding/killing the app while the chooser or picked target app is on screen) — every subsequent `Share.share()` call then fails immediately with `"Can't share while sharing is in progress"`, regardless of which post or how much later it's retried. The patch resets the flag in `handleOnStart()` instead, so returning to the app always clears any stale pending share. **Like any native change, this only reaches real users through a new Play Store release** — `src/lib/native-share.ts` also has a web-deployable stopgap (a clearer, actionable message instead of the plugin's raw error text) for the currently-live app in the meantime. If `node_modules/@capacitor/share/android/build/` ever reappears from a local Gradle run, delete it before touching `patches/` again — `patch-package`'s git diff chokes on Windows over the resulting long build-artifact paths.

**Critical**: `capacitor.config.ts` sets `server.url: "https://yukon3t.com"` — the native app's WebView loads the **live deployed site directly**, it does not bundle a local copy of `src/`/`public/`. This means:
- Any change to `src/` reaches mobile users the instant it's deployed to the web (Netlify), no app update needed. **`yukon3t.com` itself resolves to Netlify, not Vercel** (confirmed via response headers — `Server: Netlify`) — when testing a fix on a real device, a `vercel --prod` alone does nothing for it; wait for Netlify's deploy (`git push` auto-triggers it) to reach `state: "ready"` for the right commit.
- Changes to `android/app/src/main/AndroidManifest.xml` (permissions, etc.) or any other native code are baked into the APK/AAB at build time and **only reach real users through a new Play Store release** — pushing to `master` does nothing for these. Bump `versionCode` in `android/app/build.gradle` on every release build (comment there explains the current floor).
- **Built web-side, waiting on the next native release (not live):** opening yukon3t.com links tapped OUTSIDE the app (texts, WhatsApp, email, including emailed sign-in/reset links) in the app: iOS Associated Domains entitlement + portal capability, Android autoVerify intent filter + `DeepLinkGuard` change + Play signing fingerprints; see "App links". Until it ships, docs and the FAQ say such links open the browser.

## Architecture

**Stack**: Next.js 16 App Router (Server Components + Server Actions), NextAuth v5, Prisma 7 + Postgres (Neon in prod), Tailwind 4, Vitest. Deployed in parallel to **both Vercel and Netlify** off the same repo — see "Dual deployment" below.

### Server Actions are the primary write path

Almost all mutations live in `src/app/actions/*.ts` (one file per domain: `posts.ts`, `messages.ts`, `circles.ts`, `calls.ts`, etc.), not API routes. `src/app/api/` exists mainly for webhooks, cron, and things that must be a real HTTP endpoint (auth callbacks, push), plus the composers' `/api/uploads/presign` and `/api/posts` (see "Media uploads" for why). Every action follows the same shape: re-derive the actor from the session server-side, check ownership/membership (`src/lib/auth-guards.ts` + per-file checks), validate input with Zod (`src/lib/validations.ts`), then touch Prisma. Don't skip any of these three steps when adding a new action — it's the established pattern the whole app relies on for authorization.

### Never send a `User` row to a browser

Anything a Server Action returns, a Server Component passes as a prop to a `"use client"` component, or a route handler puts in JSON is serialised to the browser in full, whatever the receiving TypeScript type says. So never return or pass a `User` row fetched without a `select` (directly, nested via `include: { user: true }` / `author: true` / `members: { include: { user: true } }`, or the row `requireUser()` returns): `select` exactly the fields the UI reads, or copy them into a new object first. This applies to the signed-in user's own row too. As a backstop only, the Prisma client (`src/lib/prisma.ts`) omits `passwordHash`, `emailOtpCodeHash`, `passwordResetRequiredAt` and the three hidden-chat PIN columns from every query, and its type says so, so reading one without asking for it is a compile error; `getPasswordHash` (`src/lib/auth-guards.ts`) is how a re-authentication check reads the password hash. Email, phone, birth date, lockout and moderation columns are not omitted and still need the `select`.

### Prisma client has a custom output path

`prisma/schema.prisma`'s `generator client` outputs to `src/generated/prisma`, not the default `@prisma/client` location. Import as `@/generated/prisma/client` (or whatever's re-exported from `src/lib/prisma.ts`), not `@prisma/client` directly. This directory is gitignored — `npm install` runs `prisma generate` via `postinstall`, but a fresh clone or a CI target without that hook needs `npm run db:generate` before anything typechecks.

### pgvector HNSW indexes — Prisma will try to drop them

`Circle`/`CollabBoardPost`/`Post`/`Conversation.embedding` each carry a hand-written pgvector HNSW index (`prisma/migrations/20261010180000_restore_embedding_hnsw_indexes`). `schema.prisma` can't represent them (`embedding` is `Unsupported("vector(1536)")` and Prisma has no HNSW index type), so `prisma migrate dev` sees them as drift and writes a `DROP INDEX` line for each into **whatever migration it generates next** — that's how two earlier migrations silently removed all of them. Generate with `prisma migrate dev --create-only`, delete those `DROP INDEX` lines from the new `migration.sql`, then apply. `scripts/check-migrations-no-hnsw-drop.mjs` replays the migration files (no database needed) and fails `npm test` (via `src/lib/search-embeddings.test.ts`) and every build (first step of `scripts/migrate-if-production.sh`, before `prisma migrate deploy`) if one slips through; to add or remove an HNSW index on purpose, change its `EXPECTED_HNSW_INDEXES` in the same commit. It doesn't catch an index removed implicitly by a `DROP TABLE`/`DROP COLUMN`.

Two things are deliberately *not* index-backed. `User.embedding` has no HNSW index: the presence heartbeat updates `User.lastSeenAt` every 45s per online user, and each of those row updates would insert a fresh 1536-dim entry into it. And the Home feed's category tabs (`nearestPostIds` in `src/lib/search-embeddings.ts`) always run an exact scan even though `Post.embedding` is indexed — an HNSW scan is approximate and returns at most `hnsw.ef_search` rows (default 40) whatever the query's `LIMIT` says, and that result is a membership set for a tab, so dropping a few would make posts vanish from it. Every nearest-neighbor query goes through that file's `approximateNearest` (raises `hnsw.ef_search` via `SET LOCAL` inside a transaction) or `exactNearest`; never write a bare `ORDER BY "embedding" <=> ... LIMIT n` anywhere else.

### `src/proxy.ts` is the middleware

Next.js 16 renamed `middleware.ts` → `proxy.ts` with a renamed export (`proxy`, not `middleware`) — this is a breaking change from older Next.js training data (see `AGENTS.md`). It sets a per-request CSP nonce and builds `connect-src`/`media-src` dynamically from `R2_ACCOUNT_ID`/`R2_PUBLIC_URL` so the CSP only opens up once media upload env vars are actually configured.

### Auth: dual sign-in methods sharing one session mechanism

NextAuth v5 (Resend magic link) is the default, but `src/app/actions/password-auth.ts` implements a **fully custom** username/password path — not NextAuth's Credentials provider, because Credentials doesn't support the status/verification-gated login logic this app needs. Sessions use the **`"jwt"` strategy** (`src/lib/auth.ts`) — despite the schema having a `Session` table (kept for the Prisma adapter's other uses), neither sign-in path writes a row to it. `issueSessionCookie` (`src/lib/session-token.ts`) hand-encodes a JWT identical in shape/secret/cookie-name to the one Auth.js's own `jwt`/`session` callbacks would produce for magic-link/OAuth, so `auth()` reads either path's cookie identically. Because JWTs are stateless, there's no server-side token to revoke on logout or ban/suspend — `requireUser()` (`src/lib/auth-guards.ts`) instead checks `User.sessionInvalidatedAt` against the token's own `issuedAt` claim on every request; setting `sessionInvalidatedAt` (done on password reset and password change) is what actually forces re-authentication, not deleting anything. If you touch session/cookie logic, both paths need to keep working, and any new "kill this session" feature must go through `sessionInvalidatedAt`, not the `Session` table. **Sliding sessions:** the cookie lasts `SESSION_MAX_AGE_SECONDS` (30 days) from when it was issued, and Auth.js never slides it here (pages read it via `auth()` in Server Components, which can't set cookies, and nothing calls `/api/auth/session`), so before 2026-11-11 every member was signed out 30 days after sign-in however active. `SessionKeepAlive` (members only, layout.tsx) POSTs `/api/session/refresh` at launch/foreground at most every 12h; the route re-issues the same claims (stable `issuedAt` kept) with a fresh 30 days (re-reading `isAdmin` and `trustBand` from the database), never past 120 days from `issuedAt` (`SESSION_ABSOLUTE_MAX_AGE_SECONDS`; the last renewal is cut to end exactly at that mark, so a stolen cookie can't live forever and everyone signs in again at least every 120 days), only for an ACTIVE, non-guest, non-revoked account, and on any failure (unreadable token, DB error) answers `refreshed: false` without touching the cookie: it may extend a session, never end one. `AUTH_SECRET` must be identical on Netlify and Vercel and never rotated casually: a different value makes every existing cookie unreadable (`sessionSecret()` in `src/lib/auth-cookie.ts`).

**Forced password reset (`User.passwordResetRequiredAt`).** Set by migration `20261011150000_force_password_reset` on every account that had a password while password hashes could reach other users' browsers (see `SECURITY.md`). While it is set, `loginWithPassword` refuses the correct password, emails the normal reset link and redirects to `/sign-in?notice=reset_required`; the decision is the pure `passwordSignInOutcome` (`src/lib/password-sign-in.ts`). Magic link / Google / Apple are unaffected, and existing sessions are not ended. **Every writer of `passwordHash` clears `passwordResetRequiredAt`** (today: `resetPassword`, `setPassword`, `confirmPasswordChangeDeviceChallenge`, `fixAppReviewDemoAccount`, `scripts/fix-app-review-demo-account.ts`) — do the same in any new one. The column is in the Prisma client's global `omit` like `passwordHash`; `isPasswordResetRequired` (`src/lib/auth-guards.ts`) reads it for the signed-in user.

**Sign-in lockout, reset links, App Review demo accounts (2026-11-12).** Lockout (`src/lib/login-lockout.ts` rules, `login-lockout-server.ts` DB half, table `LoginFailureCounter`, migration `20261111120000_login_failure_counter`): failures count per account x IP and per account x device (threshold 5) and account-wide (`User.failedLoginAttempts`, threshold 20); every threshold-th failure locks 1 min, 5 min, 15 min, then 1 h; increments are single atomic statements and only the failure whose returned count hits the threshold locks. An identifier matching no account is counted the same way (keys are SHA-256, no FK), a locked attempt answers `rate_limited` and every wrong credential `invalid_credentials` (there is no `locked` error any more), so nothing reveals whether an account exists. The account-wide lock never applies to a device the account already trusts (`evaluateDevice` = known) nor to `isAppReviewDemo` accounts (they keep the per-source locks). Success clears this request's counters, a password reset all of them; the resolve-login-issues cron prunes idle rows. **Reset links** carry the token in the fragment (`/reset-password#token=`, `src/lib/reset-token.ts`); `PasswordResetToken.token` stores only its SHA-256; the page's inline script (`reset-token-client.ts`) moves the token into memory and `replaceState`s the bare path before GTM/PostHog/Sentry run, and `resetPassword` is a `useActionState` action that never redirects with the token. `src/lib/url-scrub.ts` redacts token/code-like params in PostHog `before_send`, Sentry breadcrumbs/events and GTM's `page_location`. **Demo accounts** (`src/lib/app-review-demo.ts`): the password is never in the repo; it is `APP_REVIEW_DEMO_PASSWORD` (server-only, >= 16 chars, Netlify AND Vercel, no default). Unset, demo sign-in and the admin "Fix demo accounts" button refuse; sign-in requires the typed password to equal the current env value as well as the stored hash. The button / `scripts/fix-app-review-demo-account.ts --reset-password` (env or hidden prompt, never a CLI value) hash it into every `isAppReviewDemo` account. Demo accounts can't set/change their password, get a reset email, export data or delete the account, and can't start connection requests, DMs or calls with non-demo users (or receive them).

### Cloudflare Turnstile (bot check): one widget, fails closed

Every Turnstile-gated screen (sign-in password + email link, sign-up, Apple, forgot password, verify email/device, `/try`, phone verification via `useTurnstileGate`, ad booking) uses `TurnstileWidget`; its lifecycle rules are the pure, tested `src/lib/turnstile-lifecycle.ts`. It is tap-gated (`execution: "execute"`, an owner decision the privacy policy states). Cloudflare's own `retry` is `"never"` because `"auto"` loops forever, which is the endless "Verifying…" new users reported in 2026-10. Instead a retriable error is re-run twice (2s, 5s), "Still verifying…" plus Try again shows at 8s, the check gives up at 60s, and api.js gets 2×20s download attempts. Each failure kind (blocked script, stalled, network, config incl. 110200 unknown hostname, unsupported browser, wrong device clock) has its own sentence in `shared.turnstile`. **A submit without a token is always held back in the browser.** The old "give up after 10s and let the server decide" path only produced a server-side `captcha` error while the widget kept spinning. Server: `verifyTurnstile`/`passesBotGate` return `BotCheck` (`{ ok: true } | { ok: false, reason }`), and `captchaErrorCode` maps a failure to `captcha` or `captcha_unavailable` (siteverify unreachable/5xx after one retry, or our own bad secret). **A siteverify outage fails CLOSED** (it failed open before); the owner hasn't decided on a limited fail-open. Logs carry the action and Cloudflare's error codes only, never the token or IP; outages and misconfiguration go to Sentry (at most 1 per 10 min per instance). Telemetry: PostHog `turnstile_failed` (reason, code, retries, duration bucket, native, online, path) and `turnstile_verified`, both also with platform (ios/android/web), visible (bucket of visible time), hidden_during, interactive, executed, reruns_on_resume, widget_loaded, and on a stall phase_when_stalled (executing / backgrounded_during / interactive / after_interactive / not_executed). **Stall clock (2026-11-14, after 23 of 24 `stalled` came from the native app):** the 60s only counts from execute(), while the page is visible and while Cloudflare is not showing its own checkbox (before/after-interactive callbacks; the checkbox is scrolled into view with "Tap the checkbox above"); a return from the background leaves at least 10s, a check hidden 15s+ is re-run once settled (same tap, max 2), and a stall timer that fires 5s+ late counts as a resume. `refresh-expired` is `"never"`: an expired unused token goes back to the button ("expired, tap again"), so nothing runs without a tap. `turnstile_incomplete` (not a failure; reason `not_started`, `submitted_while_checking/interactive/error`, `expired`, `left_during_check`) records the rest. Pure rules + tests: `turnstile-lifecycle.ts`, `turnstile-stall-clock.test.ts`; placement guard `turnstile-widget-placement.test.ts`. FAQ `security-check-keeps-loading`. The site key's allowed hostnames must include every host that serves the pages; the Capacitor apps load `https://yukon3t.com`, so their hostname is `yukon3t.com`.

### Media uploads: direct browser → R2, never through the Next server

Avatars, post images, and videos upload straight from the browser to Cloudflare R2 via short-lived presigned PUT URLs (`src/lib/storage.ts` mints them server-side; `src/lib/upload-client.ts` does the client-side PUT with retry/timeout logic). This is deliberate — it avoids serverless request-body limits, and images are resized **client-side via `<canvas>`** before upload rather than server-side (no `sharp`/libvips in the untrusted-image path — see `SECURITY.md`). `resizeImageFile`/`captureVideoFrame` in `upload-client.ts` read the canvas output into a plain `ArrayBuffer` before wrapping it in a `File` — this isn't stylistic, it works around a real Android WebView bug where a `canvas.toBlob()` Blob can be backed by an already-invalid temp file, failing instantly with `net::ERR_UPLOAD_FILE_CHANGED` on both the upload PUT and even a same-page `<img>` preview of it.

Real file size is re-verified server-side after upload (`HeadObjectCommand`); a presigned PUT alone can't cap size.

**Abandoned-upload sweep** (`src/lib/upload-records.ts`, hourly `sweep-abandoned-uploads` cron; full rules in `SECURITY.md`, under "Write-once public uploads"). Still dry-run only: `UPLOAD_SWEEP_DELETE` is unset and stays so until the owner decides. A dry run HEADs each unreferenced file and marks what it checked (`checkedAt`) so it advances batch by batch, also when the tripwire trips; it never deletes a file. Delete mode deletes a file only when the reference check passes its self-test (the newest in-use URL of each checked column must come back referenced; `reference_check_failed` otherwise, whatever the batch size) AND the original tripwire (`wouldTrip`: 20+ examined, 50%+ unreferenced, missing counted) doesn't trip; a batch whose unreferenced files are all definitely missing never trips, and records of definitely missing files are cleared regardless, so gone files can't stall it. Only a definite 404 counts as missing (storage errors are unknown, never deleted), and only after storage proved it can see a known file (`storage_unverified` otherwise). Delete every public-bucket file through `storage.ts` `deleteObject`/`deleteOwnedObject` (never a raw `DeleteObjectCommand`): it forgets the key's `UploadRecord` once R2 confirmed the delete. A new column that can hold an upload URL goes into `findReferencedUrls` + `MEDIA_REFERENCE_COLUMNS` ONLY if every write path stores the writer's own upload (or a server-side copy of a URL they may share): the same check decides what `deleteMediaIfUnreferenced` keeps, so a free-form URL column (`Post.linkUrl`, `AdCampaign.linkUrl`) would let anyone keep someone else's deleted media alive. Otherwise it goes into `EXCLUDED` in `upload-records-coverage.test.ts` with a reason; that test fails on a column in neither.

**Public single-PUT URLs are write-once** (security audit H3; details in `SECURITY.md`, "Write-once public uploads"). `createUploadUrl` signs `If-None-Match: *` as a header, so R2 stores the first PUT and answers every later one 412; the URL comes with `headers` the client must send exactly (`src/lib/write-once-upload.ts`), or R2 rejects it as a bad signature. A 412 counts as stored only on a retry. The public bucket's CORS must allow the `If-None-Match` header. Never re-PUT a key on purpose: mint a new one. **Never hand native code a `createUploadUrl` URL**: the installed Android builds' `GalleryPickerPlugin.uploadVideo` sends only Content-Type, so the native video path uses a one-part multipart upload (`startNativeVideoUpload`) instead.

**Every upload path needs its own retry/timeout, not just the browser one.** The native Android video picker (`GalleryPickerPlugin.java`'s `uploadVideo`, see below) streams straight from `ContentResolver` to the presigned URL entirely in Java, bypassing `upload-client.ts` and its `withRetry`/`fetchWithTimeout` entirely — it shipped as a single unretried attempt with no connect/read timeout, and failed outright on a real (not simulated) transient network blip during a longer video upload on live hardware, with no automatic recovery. Fixed with its own bounded retry + timeout loop, but the lesson generalizes: **any new upload path that doesn't go through `upload-client.ts`** (a native plugin, a different platform's picker, a future non-browser client) **needs to reimplement that same resilience itself** — it does not come for free just because the rest of the app has it.

**Composer uploads go through their own API routes, not Server Actions (2026-11-14).** Next 16 runs a tab's Server Actions one at a time through the router's action queue, with no timeout and no abort: one `createPost` / `requestUploadUrls` that never settled (an iPhone fetch suspended with the app and never failed on resume) blocked every later Server Action in the tab, so every retry of a failed post queued behind it until the app was reloaded. Presigning is `POST /api/uploads/presign` (`presignViaRoute` in `upload-client.ts`, `MIN_ATTEMPT_TIMEOUT_MS` 15s per try, under `withRetry`) and creating a post is `POST /api/posts` (`submitCreatePost`, `src/lib/post-create-client.ts`: 45s per try, 3 tries, backoff). Both routes call the same action (`requestUploadUrls` / `createPost`), which does every check itself, plus `isSameOriginUploadRequest` (`src/lib/upload-route-guard.ts`: custom header `x-yk-upload: 1`, which a cross-site page can't send without a preflight these routes never answer, and Origin == Host); `AuthError` -> 401, a throw -> 500 `server_error`. Don't move composer uploads back into Server Actions, and give any new long-running client call the same treatment.
- **Attempt lifecycle** (`src/lib/post-submit-attempt.ts`, pure, tested; `PostComposer` drives it through `createAttemptController`). `begin()` is synchronous, so a double tap is refused in the same tick. Every attempt holds the lock for a lease (`attemptLeaseMs`: 3 min + 100 KB/s for the bytes still to upload, max 60 min) and ALWAYS settles in a `finally` (returned failure, a throw = `exception`, lease out = `timeout` with the body aborted), so no path leaves the composer locked. **Key rule:** a fresh `clientRequestId` per new draft; a retry of the same draft (`draftFingerprint`: text, audience, place, event fields, file name+size+type+lastModified, never content) reuses the previous key only when the last outcome was `unknown` (lost answer, timeout, 5xx; `classifyCreateAnswer`), and `createPost` answers a key that already has a post with success, so a retry never posts twice; a definitive refusal (`no_post`) gets a new key. `retryAdvice` maps a failure to retry / repick (iOS dropped its temporary copy of the file) / wait / reload / change, worded in the `postUpload` dictionary (all five languages).
- **Failed draft** (`src/lib/failed-post-draft.ts`). The composer clears itself on Post (the optimistic card shows "Posting..."); on failure the draft (text, audience, files, URL images, native video upload, embed, GIF) is parked here and taken back by the composer (or by the failed card's Retry) with its sentence. Uploads already done for those files are kept (`releaseUploads` un-consumes the eager uploads), so Retry redoes only the failed step. One draft at a time: a newer failure replaces it and the old one's uploads are given up (`discardUpload`, which never deletes an upload a running submit has taken).
- **Picked files** (`src/lib/media-file.ts`, pure, tested with a synthetic iPhone screen recording `ScreenRecording_....MP4`): `normalizeMediaType` falls back to the extension when the reported type is generic, and maps aliases (`video/x-m4v`, `image/jpg`, HEIC/HEIF sequences); a video whose `<video>.duration` reads Infinity is scanned before it counts as unmeasurable. The Story composer's "Upload from device" input is `STORY_DEVICE_ACCEPT` = `image/*,video/*` (iOS lists videos only when a video type is named, and converts HEIC to JPEG for `image/*`; an exact image list hid every video, screen recordings included). Each Story failure has its own sentence (`storyUpload` dictionary).
- **Diagnostics.** Every failed step of a Story, share-in or post upload calls `reportMediaUploadFailure` (`src/lib/media-upload-diagnostics.ts`): PostHog `media_upload_failed` + a Sentry event carrying only `mediaDiagnostic`'s fields (surface, step, code, kind, reported type and extension only from a fixed known list else `other`, size and duration buckets, platform) plus attempt (1/2/3+) and reusedKey. Never the file name, bytes, a URL or a storage key; never throws. Not anonymous in PostHog: like any event it lands on the signed-in user's PostHog person. Privacy policy section 1 (Technical data); FAQ `photo-video-upload-failed`.
- **File pickers (`src/lib/native-picker-activity.ts`).** `openFilePicker(input)` is the only way to click an `<input type="file">` (source guards in `native-picker-activity.test.ts`: no other `.click()` on a file input, no hand-made `markNativePickerActive`, no `await` before the open except on the Android-native branch, every guarded input resets its value on change). Call it synchronously from the tap: iOS WebKit drops a programmatic click that lost the user activation. The imperative "picker in flight" guard is for **Android only** (the picker Activity pauses/resumes MainActivity like backgrounding, which everything reacting to leave/return must tell apart through `isNativePickerActive`: `HiddenRelock` must not relock and cover under the picker, `stale-build-client.ts` must not reload the composer waiting on the pick, and `capacitor-bridge.tsx`'s return refresh (`shouldRefreshOnReturn`) skips a picker's resume. Resume no longer navigates anywhere (see "App resume"), so the old reason, the resume-to-Home reset yanking the composer away mid-pick, is gone. It also stops stacked Activity launches), with real cancel detection (`armImperativePicker`: the input's `cancel` event, or focus/visibility coming back, resolves it after `CANCEL_GRACE_MS` unless a `change` arrived) and a failsafe; both clear it through `resolveStuckImperativePicker` (imperative track only, never the promise track). The bridge's old Android resume backstop that also called it was removed with the resume reset. On iOS (Capacitor iOS, iPhone/iPadOS Safari; `detectPickerPlatform`) it is never raised: the sheet doesn't background the app and WebKit fires no `change` on dismiss, so the old flag stayed up after one dismissed sheet and every later "Upload from device" / "Take a photo" tap did nothing for 60s. iOS only drops a double tap within `IOS_DOUBLE_TAP_MS` (1s).

### Profile pictures: not saveable in-app, and always private

**Deterrent (always on).** No save/download/share control is offered for a profile picture anywhere, including the enlarge view (`profile-story-ring.tsx` opens `Lightbox` with `protect`, which drops its Save button and blocks the context menu on the whole viewer). Every avatar `<img>` (`UserAvatar` in `user-link.tsx`, the story rings in `story-tray.tsx` / `profile-story-ring.tsx`, `ZoomableImage` when protected) spreads `protectedImageProps()` (`src/lib/protected-image.ts`): `draggable={false}`, `onContextMenu`/`onDragStart` preventDefault, and the `.protected-image` class in `globals.css` (no touch callout, selection or `-webkit-user-drag`). Taps still reach the surrounding link/button. The first three also use `useImageFallback` (`src/lib/use-image-fallback.ts`): a picture that fails to load (expired session, rate limit, block, deleted) shows the initial / "No photo", never a broken-image icon. A new surface that shows an avatar should use `UserAvatar` or the same helpers, and never pass an avatar to `saveMediaToGallery`/`shareNative`. The user's own avatar preview/cropper in settings is not protected. FAQ entry: `save-someones-profile-picture`.

**Private storage (the only path; needs `R2_AVATAR_BUCKET_NAME`, see `.env.example`).** Earlier versions of this section said avatar URLs had to stay public for OG/meta, web push, FCM, notification images and the native apps; that was wrong (checked 2026-10-19: none of those use an avatar URL, and the WebView loads the site same-origin, so its cookies reach `<img>`). The only reader outside the signed-in app is the bearer-token widget feed `GET /api/ambient/feed`. Pure rules are in `src/lib/avatar-url.ts`, the server half in `src/lib/avatar-storage.ts`, bucket functions at the end of `storage.ts`:
- **Bucket.** A third R2 bucket with no public domain, never the view-once one (its required 15-day lifecycle rule would delete every avatar). Browsers get 5-minute presigned PUTs for `avatar-upload/<userId>/<uuid>.<ext>` keys only (`PrivateObjectPurpose` `"avatar-upload"`); the served keys `avatar/<userId>/<uuid>-t.<ext>` (~320px thumbnail) and `-f.<ext>` (~1080px) are written by `confirmPrivateAvatarUpload`'s server-side copy, so a still-valid PUT can't swap the picture after moderation. Both images are size/type-checked and moderated (two `moderateImage` calls through 5-minute presigned GETs).
- **Stored value.** `User.avatarUrl` = `/api/avatar/<userId>/<uuid>-t.<ext>` (same-origin, relative). The backfilled form `/api/avatar/<userId>/<uuid>.<ext>` is one image for both sizes.
- **Route** `src/app/api/avatar/[...key]/route.ts`: 401 without a session (`auth()` JWT, no DB read), strict key validation (`parseAvatarRouteSegments`; the `-f` file is never addressable by path), per-user `avatarView` limiter (600/h), 404 if blocked either way, then a 302 to a presigned GET signed at the start of the hour (2h expiry, so the URL is stable and browser-cached for the hour; the redirect is `Cache-Control: private, max-age=3000`). Bytes never stream through the server. `?size=full` (`avatarFullSizeUrl`, used by the profile enlarge view) serves the full image only to the owner and accepted connections; anyone else is redirected to the thumbnail. A qualifying full-size request (and only that) HEADs the `-f` object first; if it is missing or the HEAD fails, the viewer gets the thumbnail under a 60s redirect max-age (`avatarServedObject`) and the route logs `[avatar] full-size object missing`. Without `R2_AVATAR_BUCKET_NAME` it answers 503 (after the 401), logged once per server instance. The path ends in an image extension, so `src/proxy.ts`'s matcher skips it (no page-limit cost per avatar).
- **Consumers outside the app** must not get the relative form: the widget feed uses `avatarUrlForExternalClient` (absolute presigned thumbnail), `exportMyData` uses `absoluteAvatarUrl`. In-app Server Actions (`actions/ambient.ts` etc.) keep the relative form, which the signed-in WebView loads. `src/lib/avatar-exposure.test.ts` fails if a public page or an unauthenticated API route renders/returns avatars. Previous-avatar deletion goes through `deleteStoredAvatar` (the owner's private keys only; any other URL is left alone).
- **No flag, no public path.** Every new picture goes through `requestPrivateAvatarUpload` / `confirmPrivateAvatarUpload` (`AvatarUpload`); without the bucket both answer `not_configured` (the picker says uploads aren't set up). `avatar` is not an `UploadKind`, so `createUploadUrl`/`requestUploadUrls` can't mint a public avatar URL. The `AVATAR_PRIVATE` flag, `isAvatarPrivateUploadEnabled`, `confirmAvatarUpload` and the migrate/revert scripts were removed with Stage 3 (2026-10-31); don't bring any of them back. The privacy-policy paragraph and the extra FAQ paragraph (`src/app/faq/content/private-avatars.ts`) always render.
- **Rollout stages (history).** 1 (2026-10-19): bucket + flag. 2: a backfill copied every public avatar (28) to the private bucket under the same key and rewrote `avatarUrl` to the single-image route form, writing `avatar-migration-map.json` (gitignored, local only). 3 (2026-10-31): `npm run db:delete-public-avatars` deletes the public `avatar/` objects, each only after `src/lib/public-avatar-cleanup.ts` verifies its key shape, a same-size private copy, no reference in any text/json/array column of any table outside its own route form, and agreement with the mapping file if present; `--apply` refuses while any user still has a public avatar URL. The flag and public upload path were removed in the same change. 4 (built with 1): two sizes for new uploads only; migrated avatars stay single-image because resizing needs decoding untrusted images on the server (no sharp/libvips). **Not built:** Stage 5, Android `FLAG_SECURE` / native protection.
- **Limits (say so, don't oversell):** screenshots and devtools still work for anyone signed in who is shown a picture, and a presigned link works for whoever holds it until it expires (at most 2h). The route doesn't check `sessionInvalidatedAt`. The two sizes come from the uploader's browser (a modified client can make a large "thumbnail", capped at 2MB). After Stage 3 an old public avatar URL is a 404, but a copy already downloaded or still in a cache can't be recalled. Deleting an account deletes its current avatar objects (deleteStoredAvatar, via src/lib/account-media.ts, which also removes the files behind the account's posts, comments, messages, Stories, Muses, ambient moments and own Circle covers through deleteMediaIfUnreferenced) (private bucket only).

### View-once ("for your eyes only") photo/video messages

1:1 chats only. The file never touches the public bucket: it goes browser → presigned PUT → a **second, private R2 bucket** (`R2_PRIVATE_BUCKET_NAME`, same account/credentials; no public domain; CORS for PUT+GET from the site origins; a 15-day lifecycle rule — full list in `.env.example`). `isViewOnceConfigured()` (`storage.ts`) gates everything: unset, the composer's "View once" switch isn't rendered (`viewOnceAvailable` from `messages/[id]/page.tsx`) and the actions return `unavailable`.

- **Model.** `Message.viewOnce` / `viewOnceOpenedAt` / `viewOnceExpiresAt` (sent + 14 days). `mediaType` is `IMAGE`/`VIDEO`, `content` is always `""` (no captions; `editMessage` refuses), and **`mediaUrl`/`mediaThumbnailUrl` stay NULL**. The object key exists in exactly one place, `ViewOnceMedia` (PK `messageId`, cascade). Never `include`/`select` `viewOnceMedia` in a query whose result reaches a browser — that the key isn't on the `Message` row is what keeps it out of every existing message query, `exportMyData`, reply quotes, the inbox preview, the lightbox, push payloads and the moderation queue without touching any of them.
- **Keys.** Two namespaces. *Upload* keys are `view-once/<uploaderId>/<uuid>.<ext>` (and `view-once-frame/…` for a video's still frame), minted by `createPrivateUploadUrl`; `isPrivateKeyOwnedBy` must pass before any R2 call on a client-supplied key, and only these two prefixes can pass it. A *sent* file lives under `view-once-final/<conversationId>/<uuid>.<ext>` (`viewOnceFinalKey`), chosen by the server at send time: no browser is ever given that key or an upload URL for that namespace (`PrivateObjectPurpose` doesn't include it), which is the point — the sender's presigned PUT for the upload key stays valid for up to 30 minutes and could otherwise replace the object after it was checked. `ViewOnceMedia.objectKey` is always a final key.
- **Actions** (`src/app/actions/view-once.ts`; rules and constants in the pure, unit-tested `src/lib/view-once.ts`): `requestViewOnceUpload` (member of a 1:1, not blocked, allowed type, size cap — images 25MB, **videos 64MB** because the recipient holds the whole file in memory) → `sendViewOnceMessage` (re-checks all of that, HEADs the upload for real size/type, server-side-copies it to its final key (`copyPrivateObject`), HEADs the copy — same ETag and size as the upload it just checked, type and size cap enforced again, otherwise both are deleted and the send refused — deletes the upload key, moderates **from the copy**, then creates the `Message` and its `ViewOnceMedia` in one nested create and runs the shared `afterMessageSent`, `src/lib/after-message-sent.ts`; every refusal deletes only this request's own upload keys and copy, so re-submitting an already-sent upload key can't touch a live file) → `getViewOnceContentType` (recipient only, gated like opening, returns just the MIME type: the viewer's pre-check, below) → `openViewOnceMessage` (recipient only; atomic claim `updateMany … where viewOnceOpenedAt: null`; returns a 60s presigned GET; a repeat call re-issues a link only within `VIEW_ONCE_RETRY_WINDOW_MS` (2 min) of the first open and only while the object still exists; publishes the conversation signal so the sender's chip flips to "Opened") → `finishViewOnceMessage` (recipient only, opened only; idempotent). Every deletion goes through `destroyViewOnceMedia` (`src/lib/view-once-media.ts`): object first, row only once R2 confirmed, so a failed delete leaves the row for the sweep to retry.
- **Moderation is not skipped, and is stricter than elsewhere.** A photo is checked itself, through a 5-minute presigned GET handed to `moderateImage`; a video by one still frame the sender's app captures and uploads as a companion object, deleted as soon as it's been checked (the same client-frame stand-in ordinary video messages use, with the same weakness: the client chooses the frame). Unlike every other surface, a video with no usable frame is refused (`frame_required`) and a moderation-API outage refuses the send (`moderation_unavailable`) instead of failing open — there will be nothing left to review afterwards.
- **Sweep.** `sweep-view-once` cron (`src/app/api/cron/sweep-view-once/route.ts`, every minute via `netlify/functions/sweep-view-once.mts`; answers 200 `{ skipped: true }` while the private bucket isn't configured), up to 100 per run: opened more than `VIEW_ONCE_SWEEP_AFTER_OPEN_MS` (4 minutes) ago (finish never arrived), unopened past `viewOnceExpiresAt`, or deleted-for-everyone / moderation-`REMOVED` with a row still present. The 4 minutes are the 2-minute retry window + the 60s life of a link re-issued at its last moment + a 1-minute margin: a shorter cutoff deletes a file a valid link still points at, so change those constants together (`viewOnceMediaIsDue` is the same rule). `deleteMessageForEveryone` deletes it directly; `openViewOnceMessage` also deletes on an "already viewed"/"expired" answer, but only once `viewOnceMediaIsDue` says so, for the same reason.
- **Client.** `chat-thread.tsx` renders a chip instead of media (`viewOnceState`/`viewOnceLabel`); `view-once-viewer.tsx` is confirm → pre-check → open → fetch into memory → show from a `blob:` URL → finish, revoked on close, on `visibilitychange` → hidden (only once showing: never while still downloading), and on unmount. The pre-check (`getViewOnceContentType` + `viewOnceCanPlay`) runs **before** the claim: a video type the device's `canPlayType` rejects (an iPhone `.mov` on most non-Apple browsers) shows "This video can't be played on this device. Open it on another device." and the view is not used. `finishViewOnceMessage` is called only when the media has actually rendered (`load` on the image, `loadeddata` on the video), or when the viewer closes or the element errors after a claim — not as soon as the bytes arrive. It is `aria-modal` (nav.tsx's swipe listener skips it) and `ph-no-capture`, has no save/share/download control, and blocks the context menu, drag and long-press callout. The presigned host is the R2 API host already in the CSP's `connect-src` (path-style URLs), so `src/proxy.ts` needed no change.
- **What it guarantees:** once viewed, the stored file is deleted — immediately in the normal case, within ~5 minutes (2-minute retry window + 60s link + 1-minute margin + 1-minute cron) if the recipient's app never confirms — and no server path can produce it again; nothing is kept for moderators; the bytes are never in the DB backup (only the `ViewOnceMedia` key row, while it exists). **What it doesn't:** it can't stop a screenshot, screen recording, a second camera, or a modified client keeping the bytes it was legitimately sent (native screenshots in a conversation already notify the other person via `ScreenshotGuard`); during the 2-minute window the recipient can fetch the file more than once; the `Message` row (sent/opened timestamps) is permanent; and a file orphaned without ever being attached or swept — an upload never sent (or whose key couldn't be deleted after the copy), or a row cascaded away by an account/conversation delete — is unreachable (no key anywhere) but physically remains until the bucket's 15-day lifecycle rule, which is why that rule is required, not optional.

### Hidden chats (PIN-locked, one-sided)

A user can move any conversation (1:1 or group) into a hidden area that only opens with a PIN. It is per member and one-sided: nothing changes for anyone else in the chat, and nobody is told. It is independent of secret chats (E2EE): hiding doesn't encrypt anything, a secret chat isn't auto-hidden, and the PIN has nothing to do with the E2EE passphrase.

- **Model.** `ConversationMember.hiddenAt` (same per-member pattern as `e2eeEnabledAt`; index `(userId, hiddenAt)`). `User.hiddenChatsPinHash` (bcrypt via `src/lib/passwords.ts`, 4–8 digits), `hiddenPinFailedAttempts`, `hiddenPinLockedUntil`. **Those three `User` columns are omitted from every query by the Prisma client's global `omit` (`src/lib/prisma.ts`)**, because whole `User` rows travel freely here (`requireUser()`, pages, some Server Action results); `getHiddenPinState` (`src/lib/hidden-chats.ts`) is the only reader and selects them by name. Don't remove that omit, and never return that object to a browser.
- **Files.** `src/lib/hidden-chats-rules.ts` is pure and client-safe (PIN pattern, lockout maths, `hiddenPushPayload`, `splitHiddenRecipients`, `isHiddenNotification` / `visibleNotificationWhere`, `hiddenUnlockPath` / `safeHiddenNext`, `HIDDEN_CALLER_NAME`); `src/lib/hidden-unlock-token.ts` is the signed cookie token; `src/lib/hidden-chats.ts` is the server half (queries, cookie, PIN check); actions are in `src/app/actions/hidden-chats.ts`; UI is `/messages/hidden` (`hidden-chats-panel.tsx`, `hidden-pin-field.tsx`), the "Hide chat" / "Unhide chat" item in `chat-options-menu.tsx` (now on group chats too) and `hidden-relock.tsx`.
- **The filter helpers.** `getHiddenState(userId)` → `{ conversationIds, peerIds }` (one query, memoised per request with React `cache`), also as `getHiddenPeerIds`. A "hidden peer" is the other member of a hidden **1:1**; hiding a group hides the group, not its members. `getMembersHidingConversation(conversationId, userIds)` answers "which of these recipients hide this chat". For a conversation list, filter in the query itself: `members: { some: { userId, hiddenAt: null } }`.
- **The rule: every new surface that lists conversations, peers, or message notifications to a user must apply the hidden filter**, and every new action that takes a conversation (or message) id from the client and reads or writes that chat must refuse with `hidden_locked` when `isMembershipLocked` / `isConversationLocked` says so. Covered today:
  - Conversation lists: the inbox and the hidden list (`getInboxItems` in `src/lib/inbox-items.ts`, `"visible"` / `"hidden"`), `getMyConversationsForShare`, `getForwardTargets`, `getShareableConversations` (stories). Share pickers never offer a hidden chat, unlocked or not.
  - Badges and bell: `/api/badge-counts` (unread chats, bell count and the pending-connections count) and `/notifications`, both through `visibleNotificationWhere`. That hides every row tied to a hidden conversation, plus `MESSAGE` / `MISSED_CALL` / `SCREENSHOT_TAKEN` rows whose actor is a hidden peer (`HIDDEN_PEER_NOTIFICATION_TYPES`); a hidden peer's public activity (likes, comments, posts) is deliberately still shown.
  - Peers: the three Connections lists and their counts (`connections/page.tsx`, `loadMore*Connections`, `getAcceptedConnectionIdsByActivity`), `getMyConnectionsForPicker` (live-stream audience and add-to-call pickers), the new-group and add-group-members pickers, both Collab invite pickers, inner-circle candidates / list / ambient feed and the widget feed route.
  - Notifications sent: `afterMessageSent` splits recipients; one who hides the chat gets `hiddenPushPayload()` ("YuKon3t" / "You have a new notification", opens `/home`) on web push and FCM (`type: "GENERAL"`, no conversation id in the data) and **no `MESSAGE` row**; if the lookup fails everyone gets the generic push but the `MESSAGE` rows are still written for all of them (the bell filters a hidden chat's rows at read time, so nobody loses their bell entry and nobody hiding the chat sees one). `replyToStory`'s push and the screenshot notice (`actions/screenshot.ts`: row kept, since the bell filters it, push generic) do the same.
  - Calls: `maskHiddenCallerName` makes the web push, FCM and VoIP ring payloads and `getIncomingCall` say "Private call" for a hidden peer (in `startCall` and `inviteToCall`); `notifyMissedCall` still clears the ring but leaves no named push and no `MISSED_CALL` row.
  - Thread access: `messages/[id]/page.tsx` redirects to `/messages/hidden?next=…` when hidden and not unlocked, which is also what makes "Message" on a hidden peer's profile (and any other deep link) land on the PIN prompt. `hidden_locked` is returned by `sendMessage`, `getConversationMessages` (before it marks anything read), `deleteMessageForMe`, `editMessage`, `toggleMessageReaction`, `suggestCorrection`, `removeCorrection`, `deleteMessageForEveryone`, `requestViewOnceUpload`, `sendViewOnceMessage`, `getViewOnceContentType`, `openViewOnceMessage` and `forwardMessage` (for the source chat; a hidden destination just counts as failed; the same for the share sheets' `sendToConversations`, `shareMuseToConversations` and `shareStoryToConversations`); the E2EE actions answer `not_found`. `finishViewOnceMessage` is deliberately not gated (an opened file must still be deleted). `chat-thread.tsx` turns `hidden_locked` into a redirect to the PIN prompt and back, with the typed text kept as the draft.
  - Data export: `exportMyData` (`actions/profile.ts`) leaves out, unless the PIN unlock is live (`isHiddenUnlocked`), messages sent in a hidden conversation, connections with a hidden peer, and reports filed about a hidden peer or about a message in a hidden conversation. Anything added to that export that is tied to a conversation or a peer needs the same filter.
  - Not filtered, on purpose: public search, Discover, People you may know, the public profile and its subscriber lists, posts/comments/likes, admin tools, and group-management actions (rename, leave, add members). `markMessagesDelivered` still marks hidden chats delivered, because the other person must see no difference.
- **Unlocking.** `unlockHiddenChats(pin)` sets `yukon3t.hidden-unlock`: an Auth.js-encoded token under its own salt (same pattern as the pending-login cookie in `device-challenge.ts`), httpOnly, secure, `sameSite: "strict"`, 10 minutes, fixed (activity doesn't extend it), bound to the user id (`isHiddenUnlocked(userId)`). It is cleared by "Lock now", on sign-out (`signOutAction`), after a PIN reset, and by `HiddenRelock` (mounted on `/messages/hidden` and on an unlocked hidden thread) via `navigator.sendBeacon("/api/hidden-chats/lock")` on `visibilitychange` → hidden, except while a native picker is open (`isNativePickerActive`), which hides the page the same way.
- **Lockout is in the database**, because the Upstash limiter fails open (`hiddenPin` is applied only as a second layer). `checkHiddenSecret` counts the attempt *before* checking the secret, in an `updateMany` guarded on the count it read, so parallel guesses get no extra tries. Every 5th wrong attempt since the last correct one locks: 15 min, then doubling up to 24h (`hiddenPinLockoutUntil`). A wrong account password in `resetHiddenPin` counts against the same lock.
- **Forgot PIN.** With an account password: `resetHiddenPin(accountPassword, newPin, confirmPin)`. Without one (magic-link / OAuth only): `requestHiddenPinResetCode` → `resetHiddenPinWithCode`, the emailed `SecurityChallenge` code with the new purpose `HIDDEN_PIN_RESET` (its email says nothing about what the code is for). Chats stay hidden either way.
- **Nothing may hint at use.** The Settings → Privacy "Hidden chats" row and the long-press on the "Messages" heading (`messages-heading.tsx`) are there for everyone and identical in every state; there is no count, dot or indicator for hidden unread anywhere. `hideConversation` answers `no_pin` rather than the page being told whether a PIN exists. Don't add anything conditional on having a PIN or a hidden chat outside `/messages/hidden`.
- **Known limits.** Notifications already delivered before hiding aren't recalled. After answering a "Private call" the in-call UI can show the real name. A hidden peer still appears on public surfaces, and their public activity still notifies by name. The `/messages/hidden` page itself shows "choose a PIN" vs "enter your PIN". A 4–8 digit PIN is only as strong as the lockout: its hash is trivially brute-forced offline by anyone holding the database.

### Native Android plugins (Capacitor)

`android/app/src/main/java/com/yukon3t/app/GalleryPickerPlugin.java` backs both the photo picker (`pickImages`) and the video picker/uploader (`pickVideo`/`uploadVideo`) — one native `@CapacitorPlugin` class, registered once in `MainActivity`, exposed to the web layer via `src/lib/native-gallery-picker.ts` and `src/lib/native-video-picker.ts`. Bypasses the WebView's own file-chooser (`<input type="file">`), which is unreliable there for video specifically and doesn't handle every device's photo format. Two things this file has to get right that aren't obvious from the web side alone:
- **Normalize whatever the device hands back.** `readImage()` decodes and re-encodes to JPEG anything outside the web layer's own accepted image types (confirmed live: Samsung's default HEIC/HEIF photo format has no web `IMAGE_TYPES` entry, so a HEIC pick used to vanish silently — dropped by the client's own MIME filter with no error). `handlePickVideoResult()` rounds `durationMs/1000.0` to a whole number before handing it to JS — the server's `postSchema` requires an integer, and a raw fractional value used to fail the *entire* post with a generic, misleading error.
- **Native code only reaches real users through a Play Store release** (see the top of this file) — a web-side companion fix can ship instantly, but a native-only bug (like the two above, before they had web-side backstops too) stays live for every installed user until the next release goes out.

Like any native change, this only reaches real users through a new Play Store release — see the top of this file.

### Native iOS plugins (Capacitor) — `packageClassList` gotcha

`ios/App/App/ScreenCaptureGuardPlugin.swift`/`.m` and `NativeCallKitPlugin.swift`/`.m`/`NativeCallManager.swift` are local plugins (no npm package of their own) declared directly in the App target via the classic Objective-C `CAP_PLUGIN` macro — the same pattern any Capacitor plugin uses. **This is not enough on iOS.** Unlike what the macro's own naming suggests, Capacitor iOS does not discover plugins via an Objective-C runtime class scan: `CapacitorBridge.swift`'s `registerPlugins()` only ever registers a fixed set of built-ins plus whatever class names are literally listed in `ios/App/App/capacitor.config.json`'s `packageClassList` array — and that array is generated by `npx cap sync ios` purely from npm-installed `@capacitor/*` packages' own metadata. A local, non-npm plugin's class name is never added to it automatically, no matter how correctly the Swift/Objective-C side is written. The symptom is exactly what a genuine native bug would look like — `"pluginName" plugin is not implemented on ios"` thrown from the JS side, `load()` never printing anything, even though the class compiles and is wired into the Xcode project correctly — so this is easy to chase as a Swift bug for a long time before realizing it's a registration-list problem instead.

The fix needs the plugin's exact Swift/Objective-C class name (not the JS-registered name, e.g. `NativeCallKitPlugin` not `NativeCallKit`) added to `packageClassList` in `ios/App/App/capacitor.config.json` — but that file is gitignored and fully regenerated by every `npx cap sync ios`, which would silently drop any hand-added entry on the next sync. **Use `npm run cap:sync:ios` instead of plain `npx cap sync ios`** — it runs the normal sync and then `scripts/fix-ios-package-class-list.mjs`, which re-adds `ScreenCaptureGuardPlugin` and `NativeCallKitPlugin` to the list every time. Add any future local (non-npm) iOS plugin's class name to that script's `LOCAL_PLUGIN_CLASSES` array, not just to the generated JSON directly.

`ios/App/App/capacitor.config.json` also doesn't reliably pick up every root `capacitor.config.ts` change on sync either (confirmed live: `ios.contentInset` stayed on a stale `"automatic"` in this file long after the root config moved to `"never"`, even across a fresh sync) — after any sync, diff this file against `capacitor.config.ts` rather than assuming they match.

**Running `npm run cap:sync:ios`/`npx cap sync ios` on this Windows dev machine writes Windows-style backslash path separators into `ios/App/CapApp-SPM/Package.swift`'s `.package(path: ...)` entries** (a real Capacitor CLI bug; Swift only accepts `/`). `scripts/fix-ios-spm-package-names.mjs`, chained into `npm run cap:sync:ios`, now normalizes them to forward slashes, so no manual post-sync check is needed (plain `npx cap sync ios` still leaves them broken). Android's gradle files are not affected.

**SwiftPM identity collision (`app-check`).** SwiftPM takes a local package's identity from the last path component, ignoring `name:`. `node_modules/@capacitor-firebase/app-check` therefore has identity `app-check`, the same as the remote google/app-check package that firebase-ios-sdk needs, so it shadowed it and `xcodebuild -resolvePackageDependencies` failed ("product 'AppCheckCore' ... not found in package 'app-check'"). The same script copies the patched plugin to `ios/App/LocalPackages/CapacitorFirebaseAppCheck/` (gitignored, regenerated every sync) and repoints the manifest there. Xcode/Codemagic must run `npm run cap:sync:ios` first (Codemagic already does). Any new plugin whose directory name equals a remote package identity of its dependencies needs an entry in the script's `RENAMES` table.

### Moderation gate

Post/bio/comment text (and Circle/group chat names) goes through OpenAI's moderation endpoint before being stored visible (`src/lib/moderation.ts`); flagged text is stored as `FLAGGED`, not shown. Images and video-thumbnail frames go through the same endpoint's image moderation. **Owner decision 2026-11-22:** only `MODERATION_CATEGORIES` count (sexual, sexual/minors, violence, violence/graphic, harassment/threatening, hate, hate/threatening; OpenAI's own `flagged` is ignored). **Chat text is never scanned** (sendMessage text/captions/checklists, editMessage (keeps the row's moderationStatus), suggestCorrection, forwardMessage, replyToStory, sendToConversations text, birthday wishes, checklist row edits); chat photos and video frames (incl. view-once) go through `moderateChatImage` (`CHAT_MEDIA_MODERATION_CATEGORIES`: sexual, sexual/minors) and are refused with the upload deleted. Group chat names keep moderateText. Do NOT add any category, prompt text or keyword list that flags content for concerning sexual orientation or LGBT people (owner asked, it was declined); the hate category protects them. For Post media (`createPost`), `decideMediaModeration` (`src/lib/media-moderation-hold.ts`, pure + tested) checks caption, each photo and the video frame separately: an API failure is never a flag (fails open); a must-delete category (`MUST_DELETE_MODERATION_CATEGORIES`, `sexual/minors`) is rejected and deleted at once with only a media-less `CONTENT_REMOVED` audit row (`system:media-moderation-reject`); anything else flagged is stored FLAGGED (media kept, no long-video review), with a `CONTENT_FLAGGED_FOR_REVIEW` audit row naming the post (`system:media-moderation-hold`), shown in /admin/moderation with reasons, and `createPost` answers `{ error: null, held: true }` (composer shows `heldForReview`). Nothing held is ever deleted automatically (the 14-day `sweepExpiredMediaHolds` is gone, 2026-11-22); only sexual/minors is rejected and deleted. createMuse uses the same `decideMediaModeration` (hold row `museMediaHoldAuditReason`, `(muse:<id>, VIDEO)`, under `MEDIA_HOLD_PERFORMED_BY`; a held Muse skips both video passes; an EMBED Muse with a flagged caption is stored FLAGGED) and answers `{ error: null, museId, held: true }`. An R2 HEAD failure / missing upload is `upload_check_failed` (retry message), never `too_large`/`moderation`. Comments, Stories, ads and ambient moments still refuse flagged media at upload; chat media is refused only for the two chat categories. New user-generated text or media surfaces should go through this, not bypass it.

**Hive VLM video scan (moderate-videos cron, 2026-11-18).** Videos of 60s or less are scanned with Hive's Vision Language Model (`src/lib/hive.ts`: `POST https://api.thehive.ai/api/v3/chat/completions`, model `hive/vision-language-model`, one `media_url` part with `sampling: { strategy: "fps", fps }` and `prompt_scope: "once"`, the policy prompt `VLM_POLICY_PROMPT`, strict `json_schema` response {sexual_explicit, minor_sexualized, violence, hate, unsure: boolean, reason: string} (2026-11-22: exactly four categories; explicit only, swimwear/shirtless/artistic is clean; violence includes promotion and explicit threats; hate protects protected characteristics incl. sexual orientation and gender identity, plus hate symbols; self_harm dropped; unsure only when a frame plausibly shows a kept category but is too unclear), temperature 0, max_tokens 300). It replaced Hive's Visual Moderation API (100 requests/day cap, no pay-as-you-go; its general_nsfw >= 0.75 code is gone, don't bring it back). Sampling: `vlmSamplingFps` = min(0.5, 30 / durationSeconds) from the row's `videoDurationSeconds`, 0.25 fps when unknown, so at most 30 frames (~770 input tokens each, ~USD 0.012 per 30-frame video). **Only a fully parsed answer with every category false AND unsure false is clean** (`vlmVerdictFromContent`, matrix + 32-combination test in `hive.test.ts`): a true category -> FLAGGED (comment leaves `commentCount`) plus a `CONTENT_FLAGGED_FOR_REVIEW` row naming categories + the model's reason; unsure -> held for an admin at once exactly like a give-up hold (FLAGGED, media kept, no attempt counted), reason "automatic video scan was unsure (<kind>:<id>, VIDEO): <reason>", shown on /admin/moderation as "Held for review: automatic video scan was unsure - <reason>" with the player; both rows use `performedBy` `system:video-scan-review-hold` (`VIDEO_SCAN_REVIEW_HOLD_PERFORMED_BY`; the page and the sweep read `VIDEO_SCAN_HOLD_PERFORMED_BY_ALL`), never swept. finish_reason other than "stop", empty / unparsable / extra-text / missing-or-mistyped-key answers are `bad_response` (retry, then the give-up hold). HTTP errors map as before (429 rate_limited + Retry-After, paused 405 / 402 out_of_credit, 401/403 unauthorized, 5xx provider_error, 400/413/415/422 rejected_media, e.g. a URL Hive's fetcher can't pull). Logs: one `[moderate-videos] verdict:` line per verdict (kind, id, outcome, categories, fps, frames, duration, ms, tokens; never the URL or reason text) and the `summary:` line now has `unsure=`. Known limits: sparse sampling can miss content shown only briefly; no CSAM hash matching.

**Hive video scan failures (moderate-videos cron, 2026-11-16).** Every failed scan (per-video `rejected_media`/`timeout`/`bad_response`, and the provider-wide one that stops a run) is logged with a diagnostic from the pure `src/lib/video-scan-diagnostics.ts`: kind + item id, attempt n/6, Hive's HTTP status, error code and message (URLs scrubbed), the file's extension and host (never the URL/key), duration, size and content type. Size/type come from one HEAD of the public file (`src/lib/video-scan-head.ts`: only on a failure, once per item per run, 3s cap, only URLs under `R2_PUBLIC_URL`, never fatal); the same fields go to Sentry on a give-up or provider-wide stop, and the response lists the first 10 as `failures`. **A give-up (after `VIDEO_SCAN_MAX_ATTEMPTS`) never deletes and never leaves a video public unscanned:** the Post, Comment or Muse is set FLAGGED (a live comment leaves `commentCount`), media kept, with a `CONTENT_FLAGGED_FOR_REVIEW` audit row (`performedBy` `system:video-scan-failed-hold`, reason "... automatic video scan could not process this file (<kind>:<id>, VIDEO): <diagnostic>"); /admin/moderation shows that reason and a player beside Publish/Remove. It no longer goes to the Cloudflare Stream review (which deletes what it flags); `videoLongReviewNeeded` for videos over 60s is unchanged. `sweepExpiredMediaHolds` never deletes these (it reads only `system:media-moderation-hold` rows and skips any post that also has a scan-failure row), so they wait for an admin indefinitely. No admin notification exists for any review hold, and the uploader is told nothing (the video wasn't removed). Claims are guarded on `retryDue()` as well as `videoModeratedAt: null`. **Run shape (2026-11-18, VLM):** one run reads at most `VIDEO_SCAN_PER_KIND_CAP` (3) candidates per kind, the kinds in turn (`roundRobin`, first kind rotating per tick), and scans them with `VIDEO_SCAN_CONCURRENCY` (3) workers, call starts at least `VIDEO_SCAN_MIN_START_GAP_MS` (250ms) apart (Hive allows 5 req/s), inside `VIDEO_SCAN_RUN_BUDGET_MS` (20s; not raised: Netlify cut a ~30s run and a run has up to ~4s of tail work): no claim or Hive call starts with under `VIDEO_SCAN_MIN_CALL_MS` (6s) left (per-call timeout min(30s, left)), and a call cut short with under 15s is handed back uncounted (`src/lib/video-scan-budget.ts`). A provider-wide failure seen by any worker stops new starts; calls in flight finish. A provider-wide `rate_limited` (15 min, doubling per 429 in a row, or Retry-After), `out_of_credit` or `unauthorized` (60 min) stop stores a cooldown in Upstash (`src/lib/hive-cooldown-store.ts`, key `cron:moderate-videos:hive-cooldown`, in-memory fallback), capped at 60 min, during which runs skip Hive entirely; provider-wide failures never touch `videoScanAttempts`, and every run logs one `[moderate-videos] summary:` line. Still not done: a run lock (overlapping runs are harmless because claims are guarded, but share Hive's quota).

Post videos over Hive's 60s scan limit (`HIVE_VIDEO_MODERATION_MAX_SECONDS`, `src/lib/storage.ts`) can't get Hive's synchronous body scan, so they get a second, separate automated pass instead: `src/lib/video-review.ts`, driven by the `moderate-long-videos` cron. Whether that pass runs *before* or *after* the post is publicly visible depends on length: from 60s up to `VIDEO_INSTANT_PUBLISH_MAX_SECONDS` (10 minutes) a post publishes immediately (`moderationStatus PUBLISHED`) and is removed after the fact if the pass comes back flagged — same "publish now, react if flagged" model the sub-60s Hive path and text moderation already use; only past 10 minutes does a post still publish hidden (`moderationStatus FLAGGED`) pending that same pass. Either way, `Post.videoLongReviewNeeded` (tracked independently of `moderationStatus` — see the migration adding it) is what the cron's candidate query actually keys on, not `moderationStatus`, since a PUBLISHED post in the instant-publish range still needs the pass to run. This deliberately does **not** run ffmpeg (or any native media binary) on the untrusted uploaded file — same reasoning as avoiding `sharp`/libvips on untrusted images (see `SECURITY.md`), just for video's larger CVE surface. Instead `src/lib/cloudflare-stream.ts` uploads the video to Cloudflare Stream, which is the actual decode boundary; this app's own code only ever touches Stream's own well-formed API output (thumbnail-at-timestamp images fed straight into `moderateImage`, and an AI-generated WebVTT transcript fed into `moderateText`; the profanity word list was removed 2026-11-22, so cursing alone never holds a video). A flagged video is held FLAGGED for an admin (media kept, `CONTENT_FLAGGED_FOR_REVIEW` row, `notifyVideoFlaggedForReview` tells the uploader), never deleted automatically.

This pipeline is tuned to reach a verdict as close to real time as Cloudflare's own copy/encode/caption processing allows: `createPost` (`src/app/actions/circles.ts`) kicks off the Cloudflare Stream copy the moment the post is created rather than waiting for the cron to discover it, and the cron route (`src/app/api/cron/moderate-long-videos/route.ts`) actively polls each claimed post's progress for up to ~4.5 minutes per tick (`reviewOnePost`) instead of advancing one step and returning — so most videos reach a verdict within a single tick. The cron itself runs every minute and is now just the backstop that resumes a review still in progress past its tick's budget, or one whose eager kick-off never landed — not the primary driver of latency the way it was when it ran every 5 minutes and advanced exactly one post by one step per tick.

### Calls: Daily.co

`src/lib/daily.ts` (server) creates/tokens Daily.co rooms via their REST API — there's no hand-rolled WebRTC, but there are three different front ends on top of it. Sessions that must survive navigation are mounted in one place (`GlobalCallFrame`, root-rendered in `layout.tsx`, driven by `CallSessionProvider` in `src/lib/call-session.tsx`): **1:1 calls** use `src/components/direct-call-frame.tsx`, a hand-built UI on `DailyIframe.createCallObject()` (`renderer: "direct"`); **live streams** use `live-video-frame.tsx`, also a call object (`"custom"`); only **Collab** (and Circle voice rooms, which mount their own in `circle-voice-room.tsx`) still use `src/components/call-frame.tsx`, Daily's prebuilt UI via `DailyIframe.createFrame()`. Because that prebuilt UI lives in a cross-origin `*.daily.co` iframe, both `next.config.ts`'s `Permissions-Policy` (must use `camera=*, microphone=*`, not `(self)` — Permissions-Policy can't wildcard subdomains the way CSP can) and `src/proxy.ts`'s CSP `frame-src` need to allow it, or calls silently break.

**A 1:1 call dropping out of the Daily room is not a hang-up.** It used to be: any `left-meeting` ran `endCall`, which marks the row `ENDED` and deletes the room for both people, so one side's network blip (or backgrounded app) killed the call for both. Now the only intentional exit is `hangUp()` on `CallSessionContext` (the in-call buttons), which ends the session directly without going through a Daily event — so `DirectCallFrame` can treat every `left-meeting`/`error` it sees as involuntary. **CallKit's own End on a call answered on that iPhone is a hang-up** (side/lock button on the earpiece, lock screen, system call UI; iOS build with `callEnded` only): `NativeCallManager`'s `CXEndCallAction` reports it as `callEnded` (a ring declined there stays `callDeclined`; app-requested actions are never echoed), and `IncomingCallListener` runs `hangUp()` (`planCallKitEnd`; an End that lands while the answer is still on its way ends the call once it lands) with `endCall(callId, { callKitEnded: true, voipToken })`, so the server sends that iPhone no cancel for a CallKit call that is already over. CallKit deactivates the audio session it activated when the action is fulfilled. Older builds report a mid-call End as `callDeclined`, which stays decline-only: they also leave CallKit ringing after an in-app answer, so that event can be the user dismissing a stale ring. **One tap on an out-of-app Accept answers the call** (CallKit on iOS, the incoming-call notification on Android): `IncomingCallListener` tracks answers with `createCallAnswerTracker` (`src/lib/call-answer-tracker.ts`, pure, tested), so a ring check that still finds the call `RINGING` while its answer is on its way (cold start, return from background) hides the in-app ring or auto-accepts it instead of showing a second Accept; on iOS it drains `getPendingCallEvents()` before every ring check (the live `callAnswered` event is lost while the page is suspended or not loaded), each call is answered once however many paths report it, a failed send is retried twice before the in-app ring comes back, and stale-build reloads are held while an answer is in flight. **CallKit follows answers that did not come from CallKit** (`src/lib/callkit-ring-sync.ts`, pure, tested; native `reportCallAnswered`/`endRingingCall`/`getRingingCalls` on `NativeCallKitPlugin`, feature-detected through `Capacitor.PluginHeaders` because older installed iOS builds lack them): an in-app Accept requests a `CXAnswerCallAction` through `CXCallController` (the call becomes CallKit's active call, exactly like a CallKit Accept, and the existing `call_cancelled` VoIP push ends it at hang-up); an in-app Decline requests a `CXEndCallAction`; after every ring check, each call CallKit is still ringing that the server did not report as ringing is looked up with `getCallStatus` and ended with `reportCall(endedAt:)` and the matching reason (ACCEPTED `answeredElsewhere`, DECLINED `declinedElsewhere`, MISSED `unanswered`, ENDED/unknown `remoteEnded`), never one this page is answering. App-requested actions are not echoed back as `callAnswered`/`callDeclined`. `respondToCall` also sends the responder an FCM `call_cancelled` (stops the Android ring on every one of their phones, including the one that answered in the app) and a `call:{userId}` signal (other sessions drop their in-app ring and run that CallKit check). **Other iPhones stop ringing through a VoIP cancel that never goes to the answering iPhone** (`src/lib/voip-ring-targets.ts`, pure, tested): `respondToCall(callId, accept, device)` gets `currentCallDevice()` (`src/lib/call-device.ts`: `{ platform: "ios", voipToken }` from the PushKit token in localStorage, else `{ platform: "other" }`), matched only against the signed-in user's own `VoipPushToken`s. An iPhone whose token matches: every other iPhone gets `call_cancelled` with `reason` `answeredElsewhere`/`declinedElsewhere`; Android/browser: every iPhone; an iPhone with no or a foreign token, or no device at all: none (it can't be told apart, and installed builds end their CallKit call on any cancel). An answer stores `voipOthersCleared` + `answerVoipTokenId` on the `Call` (callee) or `CallParticipant` (reset on re-invite; migration `20261107120000_call_answer_voip_device`), and every hang-up cancel (`endCall`, `leaveGroupCall`, `settleCall`, the stale-ACCEPTED sweep) goes through `sendVoipCallEndedToUser` / `planHangUpVoipCancel`: only the answering iPhone once the others were cleared, every iPhone otherwise (as before). Missed/cancelled rings still go to every iPhone (`sendVoipCallCancelToUser`). Older builds end a ring on that cancel as `unanswered` (shows as missed in Phone's Recents). **Every VoIP push reports a call (iOS 13+ kills the app otherwise and throttles VoIP delivery):** in builds with this change, a `call_cancelled` for a call CallKit isn't showing, and an `incoming_call` for a call already answered here (its push came after the in-app Accept), already reported, or (1:1 only; invites carry `invite: true` and can ring again for the same call) already over here, is reported under a fresh UUID and ended at once (`reportAndEndAtOnce`); older builds just return, which is the risk this removes. - **Peer loss** — the side still in the room shows "<name>'s connection was lost. Waiting…" and ends the call itself after `CALL_PEER_LOSS_GRACE_MS` (90s). That is deliberately the reconnect window plus a margin: shorten it below the window and the two sides race, one ending the call as the other rejoins. It checks the call row 1s after the peer vanishes and every 5s after, so an ordinary hang-up ends the call before that notice is due.
- **Foreground return** — on `visibilitychange`, a call object found no longer joined goes into the same reconnect, and a camera the OS stopped while backgrounded is turned back on if the user had it on. Audio is never touched on hide. A backgrounded camera is announced to the peer over a Daily app-message (`src/lib/call-camera-pause.ts`, same pattern as `call-hold.ts`) so they see "camera is paused" instead of a frozen frame. Hold and camera-paused are both re-sent, true or false, whenever anyone (re)joins, and cleared locally when the peer leaves — otherwise a side that was out of the room keeps a stale notice.
- **Lifetime** — a 1:1 room and both its tokens live `CALL_ROOM_LIFETIME_SECONDS` (12h, was 1h); `eject_at_room_exp` makes that the cap on one call's length. `createMeetingToken` still defaults to 1h for everything else (live streams, Collab, Circle voice mint a fresh token per join) — a 1:1 call has to pass the long lifetime explicitly because it rejoins with the token it was given at `startCall`.
- **Hang-up delivery** — both `onLeave` closures and `CallButton`'s unmount-mid-ring cancel end the call through `endCallDurably` (`src/lib/end-call-durably.ts`), which is module-level and keeps retrying `endCall` with backoff and on the `online` event for `END_CALL_RETRY_WINDOW_MS` (3 min); any resolved response stops it. Past that the peer's grace period or the cron sweep below closes the row.
- **While a session is up** — `CallSessionProvider` holds a screen wake lock where the API exists, but for a 1:1 call only while this side's camera is on (`sessionNeedsWakeLock`; an audio call has the phone at the user's ear and a WebView has no proximity sensor), and stale-build reloads are held (`useReloadHold("call", ...)`: `CallSessionProvider` while a session is up, `CallButton` while its outgoing call is still ringing, since it owns that ring and cancels the call if it unmounts mid-ring, and `IncomingCallListener` while a ring or an answer is in flight). Returning to the app never navigates (see "App resume"), so the old resume reset-to-`/home` exemption and `CallSessionContext.outgoingRingRef` are gone.

None of this helps a call in a *mobile browser* tab: the browser suspends the page in the background, so that side simply goes quiet until the peer's grace period ends the call. Only the native apps (Android's active-call foreground service, iOS's background audio mode) keep audio running in the background.

Video calls also have a front/back camera flip button (`cycleCamera()`, wired up in both `call-frame.tsx` and the 1:1 `direct-call-frame.tsx`). **Don't gate its visibility on `enumerateDevices()` device-count or `track.getCapabilities().facingMode`** — confirmed live on a real Samsung phone that both are unreliable: some Android camera HALs collapse front+back into a single `videoinput` entry that switches facing mode via constraints instead of exposing two devices, and Android Chrome's `getCapabilities().facingMode` reporting is itself incomplete (a known Chromium/Android gap) — `cycleCamera()` worked fine on that exact hardware while both signals under-reported it, hiding the button entirely. **Unanswered calls time out server-side.** The `timeout-missed-calls` cron (`src/app/api/cron/timeout-missed-calls/route.ts`, scheduled every minute by `netlify/functions/timeout-missed-calls.mts` — the route existed long before anything actually ran it) marks a call still `RINGING` 60s after it was placed as `MISSED`, deletes its Daily room, signals both sides and sends the missed-call notification, so an unanswered call ends 60–120s after being placed rather than sitting at `RINGING` forever (which is what used to produce a permanent `already_calling`). A `RINGING` row older than an hour is leftover backlog and is closed silently — no notification, no signal. Because that cron, the caller's `endCall` and the callee's `respondToCall` can all resolve the same ringing call at once, **every transition out of `RINGING` is an `updateMany` guarded on `status: "RINGING"`**, and a 0-count result means someone else already resolved it: skip the side effects (a second missed-call notification, a second room deletion) rather than repeat them. Keep that guard on any new code path that moves a call out of `RINGING`. The same goes for `ACCEPTED`: `endCall`'s hang-up write is guarded on it too, because both clients (and the sweep below) can end one connected call at the same moment.

**The same cron sweeps abandoned `ACCEPTED` rows.** Ending a connected call always needs one of its two clients to still be running and online; when neither is, the row would sit at `ACCEPTED` forever. Any `ACCEPTED` call whose `createdAt` is older than `CALL_ROOM_LIFETIME_SECONDS` — i.e. whose Daily room has expired and ejected everyone — is marked `ENDED`, its room deleted best-effort, both sides signalled and the callee's CallKit report cancelled. The threshold is that shared constant on purpose: anything younger could be a real call still in progress.

**Adding people to a connected call.** A call starts 1:1 and either person can add one of their own connections from the "Add person" button in `GlobalCallFrame`'s Leave/Minimize bar (`add-call-participant-sheet.tsx`); anyone who joined can add more, up to `CALL_MAX_PARTICIPANTS` (8) counting people still being rung. A late "Join" without being rung doesn't exist.

- **Model.** `CallParticipant` (`callId`+`userId` unique; `RINGING`/`JOINED`/`DECLINED`/`MISSED`/`LEFT`; `invitedById`; its own Daily `token`). Rows are lazy: a plain 1:1 call has none and every action takes its old path untouched. The first `inviteToCall` backfills `JOINED` rows for the caller and callee, and from then on the rows — not `callerId`/`calleeId` — say who is in the call. Re-inviting someone who declined, rang out or left reuses their row and resets its `createdAt`, which is what the ring timeout counts from.
- **Actions** (`actions/calls.ts`; shared server rules in `src/lib/call-participants.ts`, used by the cron too). `inviteToCall(callId, inviteeId)`: inviter must be `JOINED` (or a pair member of a call with no rows), call `ACCEPTED`, an accepted connection between inviter and invitee, no block either way between the invitee and *anyone* in the call (answered as a generic `unavailable`, same as an inactive account, so it can't reveal who blocked whom), invitee not already in this call (`already_in_call`) nor ringing/connected on another (`busy`), not `full`. It sends the same web push / FCM `incoming_call` / iOS VoIP payloads as `startCall` with the same `callId` and the inviter's name — so the native ring UI names only the inviter. `getIncomingCall` returns a ringing invite in the same shape as a 1:1 ring (`caller` = inviter, `othersInCall`), but with `calleeToken: null`: the callee-side prewarm would otherwise join the room muted while still ringing, which the people in it would see as someone arriving. `respondToCall` has a participant branch; `getCallStatus` answers per person (a `LEFT`/`DECLINED`/`MISSED` row reads as `ENDED` while the call carries on, which is what makes each client's `isOver` right); `getCallRoster` lists everyone for members only (`useCallRoster`, refreshed on the `call:{userId}` signal and every 10s while someone is ringing).
- **Leaving.** With participant rows, `endCall` means "I leave": a guarded `JOINED → LEFT` for that person, then `settleCall`, which ends the call (row `ENDED`, room deleted, anyone still ringing marked `MISSED` with the usual missed-call notice) only when `shouldEndAfterLeave` says so: nobody `JOINED`, or one person `JOINED` and nobody `RINGING`. So an invite outlives its inviter hanging up as long as one other person is still in the call, and a decline or ring-out that leaves one person alone ends it. Every change to who is in a call starts with `lockConnectedCall` (a no-op `updateMany` guarded on `ACCEPTED`, taken inside the transaction) so invites, answers and the end check run one at a time per call; keep that on any new path. Known gap: a 1:1 hang-up that races the very first invite on that call still ends it for everyone (the hang-up read the call before any rows existed).
- **Cron.** `timeout-missed-calls` also moves a participant `RINGING` longer than `CALL_RING_TIMEOUT_MS` (60s, the same constant the call-level timeout uses) to `MISSED` — notice, cancel push and signal, but the room is left alone — then runs `settleCall`. `sweepStaleAccepted` closes participant rows along with the call.
- **Client.** `DirectCallFrame` takes `remotes[]` from `remotesByUser` (one entry per `user_id`, newest session — `latestJoined` generalised). One remote renders exactly the 1:1 layout; two or more render a grid of tiles with name, avatar fallback and per-person hold/camera-paused state (keyed by the sender's user id from the app-message's `fromId`), one audio element each. The peer-loss grace period and notice don't run while someone this call is ringing hasn't answered (waiting for them isn't a lost connection); the status checks do, and are what end the call if that ring is declined or runs out.
- **Accepted limits.** Daily can't revoke a meeting token, so someone who left (or declined) still holds one that works until the room expires or is deleted; they'd show up in the room without being `JOINED`. A participant whose app dies without a hang-up stays `JOINED` until the call ends. `busy` treats any `RINGING`/`ACCEPTED` call the invitee is in as live, so an abandoned `ACCEPTED` row makes them unaddable until it is swept.

### Post music (built-in original tracks, 2026-11-26)

Optional music on a post: `Post.musicTrack` (nullable text, migration `20261205120000_post_music_track`; null = none, so nothing older changed). **Only a track key is stored or accepted** (`POST_MUSIC_KEYS` in `src/lib/post-music.ts`, `postMusicKeySchema` a `z.enum`); an unknown/removed key plays and shows nothing. Rule `postMusicRefusal` (createPost, editPost): the author's own NONE / IMAGE / VIDEO post, no event, not a repost/share, else `music_not_allowed`; an album's one track is on its lead (createPost writes it on albumIndex 0 only, `attachViewerState` gives every photo of the album the lead's track and `musicEditable` false on the others, editPost refuses a non-lead). `editPost` field `musicTrack`: key sets, "" removes, absent keeps.
- **No licensing, no downloads.** Ten tracks composed as code (`src/lib/music/tracks.ts`) and synthesized by `src/lib/music/synth.ts` (wavetable/FM/additive voices, seeded noise drums, circular delay + reverb so the loop is seamless by construction, RMS -20 dBFS, soft limiter under -1 dBFS; pure and deterministic). Never add samples, soundfonts, recordings or third-party audio. `synth.test.ts` renders every track and checks loudness, peak, DC, the loop seam, determinism and that tracks differ; changing how anything sounds = bump `MUSIC_SYNTH_VERSION` (`render-track.ts`) so device caches re-render (a score change re-renders on its own: `trackCacheId` hashes it). A new track = score + key + name/mood in `feed.composer.music` in all nine languages (`post-music.test.ts`).
- **Why an `<audio>` element playing a device-rendered WAV** (not Web Audio, not shipped files): no encoder exists here for a gapless compressed loop (MP3/AAC padding gaps the seam) and WAV assets would be ~1 MB each; a media element behaves like the video sound it replaces on iOS WKWebView (silent switch, audio session, background) and follows the same gesture rules, whereas an AudioContext is muted by the silent switch and gets interrupted on backgrounding. The WAV is rendered on the main thread in ~12 ms slices (`renderScoreAsync`; no Web Worker: Turbopack emitted `new Worker(new URL(...))` as a raw .ts asset, so it would never have run on Vercel), kept in Cache Storage (`yk-post-music-v1`) and memory (blob: URL; CSP `media-src blob:` already allowed). Nothing is fetched before a tap (low-data safe).
- **Playback** (`src/lib/post-music-playback.ts` pure coordinator + tests; `post-music-player.ts` DOM glue): ONE shared `<audio>` (SELF_HELD, so `video-playback-guard.ts` leaves it alone), one owner at a time; a call hold, a page hold (new `subscribePageMediaHold`), the page hidden and any other audible non-live media starting all interrupt it (no auto-resume for a chip); nothing starts while blocked; a superseded start never plays. `unlockPostMusic()` is called synchronously in every tap that can make music audible (chip, sound/play buttons, video tap, full screen, previews) so iOS lets it play after the async render. Photo/text posts: `PostMusicChip` (44px, aria-pressed, named track), tap-only, pauses when its card's `[data-post-music-scope]` leaves the viewport. Videos: `useVideoMusic` mutes the video and follows play/pause/waiting/seek/loop (video time mod loop, realign over 0.3s drift) only while the feed sound setting (`useFeedVideoMuted`) is on.

### Motion: no bounce anywhere, tweens only

Owner rule (2026-11-13): no picker, sheet, menu, dialog or press may bounce. There are no springs in `src`. `APP_DEFAULT_TRANSITION` (`src/lib/motion-defaults.ts`: tween, 0.2s, ease `[0.22, 1, 0.36, 1]`) is the root `MotionConfig` default (`motion-provider.tsx`; no nested MotionConfig may replace it), because motion's own default for x/y/scale is an underdamped spring; every animation still sets its own `transition`. **In motion 14, `damping` is the raw physics coefficient, not a ratio:** any of stiffness/damping/mass makes the spring physical (defaults 100/10/1) and `duration`/`bounce` are then ignored, so the earlier `{ type: "spring", damping: 1 }` "critically damped" fix was a damping ratio of 0.05, a long wobble. Drag snap-back uses `bounceStiffness: 600, bounceDamping: 50` (ratio ~1.02). Guards: `src/components/motion-defaults.test.ts` (scans all of `src`: no spring literal outside the empty `SPRING_ALLOW`, no `bounce:` option, no press/hover scale above 1, every bezier within 0..1, non-wobbling drags, CSS keyframes that overshoot only if in `KEYFRAME_ALLOW`) and `sheet-springs.test.ts`, both on `src/components/motion-guard.ts`. ### Analytics: PostHog (session replay + product analytics)

`src/lib/posthog-client.ts` (init/identify/reset) + `src/components/posthog-provider.tsx` (mounted once, unconditionally, in `layout.tsx`) — replaced Microsoft Clarity (2026-09) rather than running both, since two session-replay tools recording the same sessions doubled the client-side recording overhead and the privacy-disclosure surface for no real benefit. **Privacy**: this app has a real end-to-end-encrypted secret chat feature (`src/lib/e2ee/`) whose entire point is that not even YuKon3t's own servers can read the plaintext — a third-party screen recorder capturing that same text as rendered pixels would quietly undermine that guarantee regardless of the encryption itself. ### Domain model (see `prisma/schema.prisma`)

- **Circles** (communities) → **Channels** → `ChannelVoiceParticipant` for live voice. A PRIVATE Circle's owner or co-admin (`MODERATOR` membership; not `isCircleAdmin`, no site-admin shortcut) can invite their own accepted connections (`inviteToCircle`, max 50 per request, own `circleInvite` limiter 10/h) as `CircleInvite` rows (PENDING/ACCEPTED/DECLINED, no expiry, an admin can cancel a pending one); eligibility and the re-invite rules (DECLINED, or ACCEPTED but no longer a member, reset to PENDING) are in the pure `src/lib/circle-invite.ts`. **An invite is only acceptable while its inviter can still invite** (`canInviterStillInvite`: owner, or still a MODERATOR member, account ACTIVE); otherwise accepting refuses with `invite_expired` and deletes the row, and the invitee is never shown it (`loadStandingCircleInvites`). The admins' Invited list marks such a PENDING invite `stale` (`isStaleCircleInvite`, loaded by `loadCircleInvitesForAdmins`, which selects only the inviter fields the check needs and drops them) with a "can no longer be accepted" label, still cancellable; re-inviting that person resets the same row to PENDING from the current inviter and notifies again, like a DECLINED one. Resets and the accept/delete claims are guarded on both status and `inviterId`. Inviting someone with a PENDING join request approves it instead. `respondToCircleInvite` (invitee only, guarded PENDING claim, blocks re-checked with inviter and owner) adds a MEMBER and notifies the inviter (`CIRCLE_INVITE_ACCEPTED`) and the other admins (`CIRCLE_JOINED`), never subscribers; `joinCircle` on a private Circle accepts a pending invite. `CIRCLE_INVITE` is bell + FCM push. Going PUBLIC deletes pending invites. `createCircle` is idempotent against a double-submit: the same creator, name (case-insensitive) and parent within 2 minutes resolves to the Circle already made (checked before the rate limiter and again under a `pg_advisory_xact_lock` in the creating transaction, rules in the pure `src/lib/circle-create-dedupe.ts`) with no repeat notifications, and the wizard's final button disables itself while pending.

### Dual deployment: Vercel + Netlify, different mechanisms

Both are live off this repo, same Neon database. **Netlify auto-deploys on `git push` to `master`.** Vercel does **not** auto-deploy from this repo config — it needs an explicit `vercel --prod`. A change isn't "live everywhere" until both have happened. Env vars must be set separately on each platform (`vercel env add` / `netlify env:set`) — a var only present in local `.env` silently leaks into a Vercel build (Next's own env loading finds it) but is simply absent on Netlify. See `SECURITY.md` for the full incident history on this, including a Windows-specific `netlify deploy --prod` bundling bug (use git-push/build-hook deploys instead of the local CLI on Windows) and a GitHub-cross-account webhook mixup.

Both platforms' production builds run `scripts/migrate-if-production.sh` before `next build` (wired into `package.json`'s `build` script for Vercel, and directly into `netlify.toml`'s `command` for Netlify, since Netlify's build bypasses `package.json`'s `build` script entirely). That script runs `prisma migrate deploy` only when `VERCEL_ENV`/`CONTEXT` is `production` — a preview/branch build or local `npm run build` skips it, so an unmerged migration never touches the shared prod database early. Before this existed, a schema migration applied to local dev only (via `npm run db:migrate`) would deploy code that silently 500'd in production until someone applied the migration to Neon by hand — if you ever bypass this script (e.g. deploying a prebuilt artifact), apply the migration to production yourself first.

**Netlify build heap.** `netlify.toml` sets `NODE_OPTIONS = "--max-old-space-size=6144"` under `[build.environment]`: the type-check step of `next build --webpack` ran out of Node's default ~2 GB heap on 2026-11-14 and every Netlify build failed ("Failed to type check") while Vercel, which builds with Turbopack, kept succeeding. Diagnose a failed Netlify build with `npx netlify-cli logs --source deploy --since 1h`, and check the deploy state before trusting "it's pushed".

**Netlify secrets scan (`SECRETS_SCAN_OMIT_KEYS`).** Netlify fails the build when the VALUE of a secret-looking environment variable stored on Netlify appears in repo files or build output, even if that value is public. `APNS_TEAM_ID` holds the Apple Team ID `3465L6ZHRJ`, which the apple-app-site-association document has to contain (`IOS_TEAM_ID` in `src/lib/app-links.ts`, also the Xcode project's `DEVELOPMENT_TEAM`), so the first deploy of that file failed on 2026-11-15. `netlify.toml` sets `SECRETS_SCAN_OMIT_KEYS = "APNS_TEAM_ID"` under `[build.environment]` (db2392d): only that key is skipped, every other secret is still scanned. Any other non-secret value that is also a Netlify env var (a public id, a bundle id) will fail the build the same way once it lands in the repo: add its KEY to that list rather than disabling the scan. Diagnose with `npx netlify-cli logs --source deploy --since 30m`.

`SECURITY.md` also documents the full list of implemented security controls (CSP nonce, rate limiting via Upstash, SSRF-guarded remote image fetch, etc.) and known accepted gaps — read it before changing anything auth/upload/moderation-adjacent.

**Rate limiting** (`src/lib/rate-limit.ts`): every limiter counts in its own Redis key space, `rl:<name>` after its key in `limiterDefinitions` (the few that already passed an explicit prefix, e.g. `subCircleCreate`, keep it so their counters didn't reset). Before this they all shared Upstash's default prefix, so two limiters with the same identifier and window length counted against one counter — viewing Muse videos used up the message-send budget. A check times out after 1s rather than the library's 5s, and both a timeout and an outright Upstash error are logged with a `[rate-limit]` line and then decided per limiter. Ordinary limiters **fail open** (the request is allowed), so a slow or down Redis degrades to unlimited, never to an outage. The limiters that send email or SMS or guard a password re-entry (`signIn`, `passwordSignUp`, `passwordResetRequest`, `emailOtpSend`, `phoneVerifyRequest`, `deviceChallengeSend`, `accountReauth`) **fall back to a database counter** (`src/lib/rate-limit-db-fallback.ts`, table `RateLimitFallback`, one atomic upsert per check; it registers itself through `globalThis` because the proxy bundles `rate-limit.ts` and must stay free of Prisma) and refuse the request if the database fails too; the paid model limiters (`transcribeAudio`, `translateModelCall`, `translateGlobal`, `brandedVideo`) **fail closed** with no fallback. The proxy reserves page-limit tokens 10 at a time (`src/lib/page-limit-credits.ts`) to spend far fewer Upstash commands, so the quota is harder to exhaust. Set Upstash usage alerts: if the quota runs out, ordinary limiters stop enforcing. Those reports are throttled to one per 10 minutes per server instance per failure kind (thrown error vs. timeout), with the number suppressed in between attached to the Sentry event, because `src/proxy.ts` runs a check on nearly every request and an exhausted Upstash plan would otherwise send one Sentry event per request. Every proxy check also costs an Upstash command, so `/api/cron/*` (bearer-authenticated), `/api/health`, `/api/build-id` and the static `/sw.js`, `/offline.html`, `/manifest.webmanifest`, `/robots.txt` and `/sitemap.xml` skip the `pageRequest` limiter (`PAGE_LIMIT_EXEMPT_*` in the proxy); everything else, including every other `/api` route, auth callbacks and Server Actions, stays limited. **The page limit is three buckets, not one** (`pageLimitChecks` in `src/lib/page-rate-limit.ts`, sizes in `rate-limit.ts`): a request carrying the device-id cookie counts against `pageRequestDevice` (per device) and `pageRequestNetwork` (per client IP, a high ceiling for shared Wi-Fi and carrier CGNAT), so it costs two Upstash commands; one without the cookie counts against the strict per-IP `pageRequest`; one with no client address isn't counted. The client IP comes from `clientIpFromHeaders` (Netlify's `x-nf-client-connection-ip` first, which a client can't set), shared with `src/lib/client-ip.ts`. A single 300-a-minute per-IP bucket refused two phones on one Wi-Fi mid-call on 2026-10-14 and left the app on a bare text page: a refused page load now gets a small self-reloading page in the reader's language (`rateLimitPage`), anything else a bare 429, both with `Retry-After`.

### Realtime layer (Supabase Realtime Broadcast) — replaced all polling (2026-09-16)

Every "live" UI in this app — nav badges, chat/messages, calls, live streams, Circle voice channels, Collab sessions, the Home feed — used to work by polling a Server Action/API route on an interval (`usePolling`, `src/lib/use-polling.ts`, since deleted). All of it now runs on Supabase Realtime Broadcast instead: `src/lib/realtime-server.ts` (`publishEvent`, server-only) and `src/lib/realtime-client.ts` (`useRealtimeEvent`, the client hook), with every channel name centralized in `src/lib/realtime-channels.ts` (`REALTIME_CHANNELS`).

**Design — broadcasts are thin signals, never the payload itself.** This app's authorization lives entirely in Server Actions/API routes (see "Server Actions are the primary write path" above); Supabase Realtime's own access control (private channels + RLS) is built around Supabase Auth, which this app doesn't use. Rather than bridging two auth systems, every channel is a **public** broadcast carrying only "something changed, go refetch" (e.g. `{ conversationId }`, never message content) — the client's existing, already-authorized fetch is what returns the real data, exactly as it did on a poll tick. A channel name leaking is not a security issue: at most it tells an eavesdropper "activity happened," never what that activity was. Only Supabase's Realtime service is used — the actual data stays on Neon, and Supabase's own Postgres/Auth are untouched.

`useRealtimeEvent(channel, event, handler)` also refetches once on tab-focus-regain as a safety net against a signal missed while the WebSocket was disconnected (backgrounded mobile WebView, a brief network drop) — a one-shot check, not a timer. That resync is shared across every instance of the hook (`createResyncScheduler` in `realtime-client.ts`), not run per instance: one `visibilitychange` listener runs each distinct handler once (a function passed to several instances — e.g. one refetch on two channels — is deduped), spread over a random 0–2s, and never the same handler twice within 10s (a too-recent one is deferred to the end of that window, not dropped). Before this, foregrounding the app on Home fired ~10 requests in the same tick. **Calls opt out of the delay**: pass `{ resync: "immediate" }` as the 4th argument (used by `incoming-call-listener.tsx`'s two checks and `call-button.tsx`'s caller-side status check) and that handler resyncs the instant the tab is visible, on every foreground, ignoring the 10s window — someone opening the app mid-ring must see the banner now, and one extra request is the cheaper mistake. Don't reach for it for anything that isn't that latency-critical; it's exactly the thundering herd the scheduler exists to prevent.

**One Supabase channel per topic, reference-counted** (`createChannelRegistry`). `RealtimeClient.channel(topic)` returns the *existing* channel object for a topic that's already open, and `removeChannel()` leaves that one shared channel outright — so when each hook instance opened and removed "its own" channel, the first of two components on a topic to unmount (`CallButton` and `IncomingCallListener` on `call:{userId}`; the three Home components on `live-streams`) silently unsubscribed the other until the next full reload. Every subscriber now goes through the registry, which joins on the first listener and leaves only after the last one goes (deferred a microtask, so a same-commit handoff doesn't leave + rejoin, and a re-request during a still-pending leave waits for it to finish). Never call `supabase.channel()`/`removeChannel()` directly from a component.

**Channels everyone hears at once are throttled on the client, not just subscribed to.** A `home-feed:*` signal fires for every public post by anyone and reaches every open Home tab in the same instant, so `post-feed-section.tsx` coalesces them (`createSignalThrottle`): each tab waits a random 0–5s before fetching and makes at most one signal-driven fetch per 20s however many posts land in between. Two cases bypass it and fetch right away — the focus resync, and any signal that arrives while the viewer's own post is still sending (it's most likely the one announcing it). Live-stream signals carry a `kind` (`comment`/`presence`/`stage`, see `src/lib/live-stream-signal.ts`) so a listener refetches only what that kind is about instead of everything — `presence` (viewer counts) is additionally throttled to one refetch per 5s; a missing or unknown kind (the focus resync's null payload, a server still on pre-`kind` code mid-deploy, a kind this client's cached JS doesn't know yet) falls back to a full refetch, so adding a kind is safe to deploy in either order. The kind is the *whole* payload — still never data. The global `announcements` signal just sets the what's-new badge locally (`use-nav-badges.ts`) rather than sending every signed-in client to `/api/badge-counts` at once.

On the server, `publishEvent` has a 2s timeout (it's awaited inside nearly every mutation — a hung Supabase call must not hang the write), and `publishEvents` sends a fan-out as one batched request per 100 events instead of one HTTP call per recipient (see `afterMessageSent` in `actions/messages.ts`). Both stay best-effort and never throw.

**Not migrated, deliberately**: `recordLiveStreamHeartbeat` (a periodic "I'm still here" keepalive the `end-inactive-streams` cron watches for, not an event-driven concern) keeps its own timer, as does anything else that's fundamentally "prove liveness on a schedule" rather than "refetch when something changed."

Setup: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (client-safe), `SUPABASE_SECRET_KEY` (server-only) — see `.env.example`. No SQL/RLS/table setup needed in the Supabase project at all, since it's used purely as a signaling relay.

### Automated database backups

A daily encrypted logical backup of every table runs via the `backup-database` cron (`src/lib/db-backup.ts`), same Netlify Scheduled Function pattern as every other cron. It uploads to a **separate, private** R2 bucket (`BACKUP_R2_BUCKET_NAME`) — never the public media bucket (`R2_BUCKET_NAME`), which serves every object under it to anyone via `R2_PUBLIC_URL`. The cron no-ops (503) until `BACKUP_R2_BUCKET_NAME`/`BACKUP_ENCRYPTION_KEY` are actually configured; see `SECURITY.md`'s "Automated database backups" section for the full threat model and one-time setup steps. Restore is manual and deliberate only: `npm run db:restore-backup` (`scripts/restore-database-backup.ts`), never automatic.

### Scalability pass (2026-09-14)

A concurrent-user-focused audit (not a security one) found and fixed the real bottlenecks, in priority order:

- **Nav badge polling consolidated 4→1.** Messages/connections/notifications/announcements unread-counts used to be 4 independent `usePolling` loops (`src/components/nav.tsx`, `notification-bell.tsx`, `whats-new-bell.tsx`), each re-running `requireUser()`'s own DB lookup, all mounted for every signed-in user on every page. Now one `/api/badge-counts` route (`requireUser()` once, 4 count queries in `Promise.all`) backs one shared `useNavBadges` fetch (`src/lib/use-nav-badges.ts`); `NotificationBell`/`WhatsNewBell` are now presentational, taking `count`/`unread` as props instead of self-fetching. `post-feed-section.tsx`/`live-stream-strip.tsx`/`incoming-call-listener.tsx` were at the time deliberately left as their own separate polls — each already just one poller with genuinely different data/latency needs (incoming-call in particular was latency-critical at 5s) — but as of the 2026-09-16 realtime migration (see "Realtime layer" above), none of these poll at all anymore; every one of them, plus everything else in this list, moved to Supabase Realtime.
- **Unbounded reaction/comment/story-viewer queries fixed.** `toggleLike`/`toggleCommentReaction` used to ship one row per reactor on every single like/react click — a viral post's full reactor list re-downloaded by every subsequent click. Now aggregated in Postgres via `groupBy` (`emoji`, `_count`) instead, returning `{emoji, count, reactedByMe}[]` (`src/lib/reactions.ts`) — correct at any scale, not just capped. `getPostComments`/the standalone `/post/[id]` page share one helper now (`src/lib/comments-data.ts`) that also batches this aggregation across every comment on the post in one query, and caps comment load at 500 (oldest-first — safe, since a reply's parent always precedes it, so `buildCommentTree` never orphans one). `getStoryViewers` similarly capped at 200. Message reactions were deliberately left untouched — at the time a conversation was always exactly 2 people, so a message could never have more than 2 reactions. That premise is stale now that group chats exist (see "Domain model"): a message's raw reaction rows are bounded by the group's member count, not by 2. `ReactionBar` (shared by posts/comments/messages) now renders pre-aggregated summaries; `chat-thread.tsx` adapts its still-raw message reactions via `summarizeReactionRows` at render time rather than duplicating the DB-side aggregation for a case that doesn't need it.
- **Open question, unverified**: whether production `DATABASE_URL` (Vercel/Netlify) actually uses Neon's pooled (`-pooler`) endpoint rather than a direct connection. `src/lib/prisma.ts`'s own comment already flags this as what actually caps concurrent capacity in a serverless deployment — each function instance gets its own small connection pool (`max` defaults to 10 since 2026-10-31; the sizing argument, which assumes the pooler, is in `src/lib/db-pool.ts`), and without a real pooler in front, enough concurrent instances will exhaust Postgres's own connection limit regardless of how small each instance's pool is. Check both platforms' `DATABASE_URL` against Neon's dashboard connection string (the pooled one has `-pooler` in the hostname) before assuming this is handled.

**Second pass (2026-10-10)** — aimed at what happens when many clients react to the same thing at the same moment, plus two things that had silently stopped working. Each is documented where it lives rather than repeated here:

- Realtime: shared reference-counted channels (a real cross-component unsubscribe bug), shared/deduped/jittered foreground resync with an immediate option for calls, coalesced `home-feed` signals, `kind`-scoped live-stream signals, batched `publishEvents`, a 2s `publishEvent` timeout — see "Realtime layer".
- Search: the pgvector HNSW indexes two Prisma-generated migrations had dropped are back, with a guard against it happening again — see "pgvector HNSW indexes".
- Rate limiting: per-limiter Redis prefixes, 1s timeout, fail-open with logging (email/SMS-sending limiters fall back to a database counter, paid model limiters fail closed) — see the "Rate limiting" paragraph under "Dual deployment".
- Calls: `timeout-missed-calls` is actually scheduled now, and every transition out of `RINGING` is guarded — see "Calls". 1:1 calls also reconnect instead of ending on a dropped connection, and stale `ACCEPTED` rows are swept.

**Known open items, not yet addressed**: production `DATABASE_URL` using Neon's pooler is still unverified (the bullet above); media is served straight from the R2 public URL with no cache headers or CDN in front (verify what `R2_PUBLIC_URL` actually points at); the video crons declare `maxDuration = 300`, an assumption that hasn't been checked against Netlify's own function limits; announcement broadcast and subscriber-notification fan-out (`notifySubscribers`) still run synchronously inside the request that triggers them; search's exact-match path is unindexed `ILIKE`; nothing ever prunes `Notification` or `AnalyticsEvent` rows; and the database backup builds the whole dump in memory before uploading.

## Home / Muse rotation (2026-11-17)

Owner decision: Home (every category tab) and Muse default to a fresh recency-weighted mix every 15 minutes; the "Latest" switch (`FeedOrderToggle`, cookie `yukon3t.feed-order` = `latest`, read during SSR by `getFeedOrder` in `src/lib/feed-order-server.ts`) gives exactly the old newest-first behaviour. The admin "include private posts" view is always newest first. Pure rules and paging: `src/lib/feed-rotation.ts` (read its header); Prisma id sources: `feed-rotation-sources.ts`; Home hydration: `home-feed-rotation.ts`.
- **List per (viewer, feed key, bucket)**, bucket = floor(now / 15 min), S = its start: fresh head (created in [S, t], t = first page served, plus the viewer's own posts from [S - 24h, S), newest first), then the rotated body (ids created in [S - 7d, S), at most 500, keyed by Efraimidis-Spirakis ln(u)/w with u = hash(viewer:feed:bucket:id) and w = 2^(-age/36h)), then a newest-first (createdAt, id) keyset tail. Seed is viewer id + feed + clock only: no behavioural data, nothing stored, no cache (Upstash deliberately not used for this).
- **Cursor** (`r1.` + base64url JSON): `{m:"r", b, t, i, l, la, lo, x}` inside the list (a deleted last item `l` is put back where its key placed it, else offset `i`) or `{m:"c", b, at, id, x}` in the tail. A bucket in the future or begun > 6h ago restarts from the top. Home's route takes `cursor` (rotated) or `before` (newest first); `getMuseFeed` treats an `r1.` cursor as rotated and a plain id as newest first, and with no cursor follows the switch. `/muse/[id]` starts the mix without that Muse (`permalinkRotationCursor`, `x`).
- **Every id query and the card query use the feed's existing where** (`getListablePostsWhere` + category; Muse PUBLISHED + `getBlockedEitherWayIds`), so nothing listable changes. Never reshuffle mid-scroll: `PostFeedSection`/`MuseFeed` keys include the order, never the bucket; `refetchNewer` asks for posts after `newerPostsAfter(posts, servedAt)` (not posts[0]) and only prepends. FAQ `feed-muse-fresh-mix-latest`; privacy policy sections 2 and 10.

## Guest preview ("Explore YuKon3t as a guest", /try)

A no-sign-up, read-only visit for sharing links like `https://yukon3t.com/try?ref=reddit`. Off unless `GUEST_PREVIEW_ENABLED=1` (server-read, both Vercel and Netlify; status card on `/admin/system`): off, `/try` is a 404 and every guest session ends at its next request. Migration `20261026120000_guest_preview` (`User.isGuestPreview`, `AnalyticsEventType.GUEST_PREVIEW_STARTED`).

- **Identity.** ONE shared `User` row with `isGuestPreview` (email `guest-preview@yukon3t.invalid`, no password/username, `discoverable: false`, `postsVisibility: HIDDEN`, never onboarded, `newMemberAnnouncedAt` pre-set, alerts off), created on first use by `ensureGuestPreviewUser` (`src/lib/guest-preview-server.ts`), which never repurposes a non-flagged row holding that address. It can't be signed in to (`signIn` callback and `loginWithPassword` refuse it). Each visitor gets their OWN session cookie (`issueGuestSessionCookie`: the normal JWT plus a `guest` claim). Lifetime is fixed, `GUEST_PREVIEW_SESSION_MAX_SECONDS` (2h) from `issuedAt`, not sliding; enforced in `auth.ts`'s `jwt` callback (returns null: signed out everywhere, avatar route included) and again in `requireViewer`. Pure rules: `src/lib/guest-preview.ts`.
- **Read-only, deny by default.** `requireUser()` (so `requireVerifiedUser`/`requireAdmin` and every write) throws `GuestReadOnlyError` (an `AuthError`) for a guest. `requireViewer()`/`requireVerifiedViewer()` let a guest through and are for READ paths only: `page-guards.ts` (every page), `/api/badge-counts` (always zero for a guest, writes nothing), `/api/feed/[category]/latest`, and the Server Actions in `GUEST_READ_ALLOWED` of `src/lib/guest-preview-coverage.test.ts`. That test scans every exported action in `src/app/actions` and fails unless it calls a member guard (directly or via a same-file helper) or is allow-listed (`GUEST_READ_ALLOWED` / `PUBLIC_NO_SESSION` with a reason), and fails if anything else calls `requireViewer`. A new read action a guest needs must be added there on purpose; a new write action needs nothing (it is refused by default). Never write for a `requireViewer` user without checking `isGuestPreview`.
- **Members-only pages** render `GuestGatedScreen` for a guest (messages, connections, notifications, settings, create pages, invite, the guest's own profile; list in the coverage test). The guest row is excluded from search, Discover, people-you-may-know, semantic search, new-member alerts (both sides) and the admin analytics account counts; `requestConnection`/`startDirectMessage`/`toggleSubscription` refuse it as a target, and `/u/<guestId>` is a 404 for others.
- **Client.** `GuestPreviewProvider` (root layout, around `<main>`) shows the banner (Sign up free, Give feedback = `NEXT_PUBLIC_FEEDBACK_URL` or the support mailto) and turns, for guests only, any form submit (except `data-guest-ok` forms: search/filters/the sheet) and any click inside `data-guest-block` into the "Create a free account to do this" sheet; its Sign up / Sign in buttons call `leaveGuestPreview` (ends the guest session, never a member's). Components with handler logic use `useGuestPreview()` (Muse, Story viewer, live room/preview, Collab session, Circle voice). The layout mounts no call listener, FCM/push, presence, share-target, review prompt or translation for a guest; PostHog never records or identifies a guest. Server enforcement does not depend on any of this.
- **Abuse limits.** `startGuestPreview` (honeypot + `passesBotGate` Turnstile + `guestPreviewStart` 10/h per IP + `guestPreviewStartGlobal` 3000/h; never replaces a member session; records `GUEST_PREVIEW_STARTED` with the sanitized `?ref=` tag). Guests can't watch live streams (joining makes a Daily viewer token), translate, or record views. FAQ `try-without-signing-up`; privacy policy sections 1, 7, 10.

## Search engines and store listings (SEO, 2026-11-18)

- **No per-language URLs, except `?lang=` on two pages.** A request's language is the cookie, else Accept-Language, else English, so a crawler only ever saw English. `src/lib/seo-locale.ts`: on `/` and `/faq` only (`LOCALIZED_SEO_PATHS`), exactly one supported `?lang=xx` makes `src/proxy.ts` set the request header `x-yukon3t-seo-locale` (any copy a client sends is deleted first), and `getLocale` (`src/lib/i18n/server.ts`) lets it win over cookie and Accept-Language for that request. Nothing is stored; `LanguagePicker` drops the parameter after a change. Both pages were already dynamic (session/cookies), the service worker never caches pages and the apps never send `?lang=`, so there is no cache fragmentation. Add a page to `LOCALIZED_SEO_PATHS` only if all of its text is translated.
- **Metadata** (`src/lib/seo.ts`, `localizedPageMetadata`): landing and FAQ titles/descriptions are the dictionary's `seo.landing` / `seo.faq` (all nine languages; `seo.test.ts` keeps titles <= 60 and descriptions 140-160 characters). Canonical = the address asked for (`/` or `/?lang=xx`, self-referencing, never canonicalised to the plain address, which would make Google drop the language versions); hreflang lists the nine `?lang=` addresses plus `x-default` = the plain address; `og:locale` / `og:locale:alternate`. In production every canonical/sitemap/structured-data URL is `https://yukon3t.com` (`siteUrl`), whatever `NEXT_PUBLIC_APP_URL` says. Other public pages (sign-in, sign-up, advertise, legal) have an English canonical only.
- **Structured data** (`JsonLd` in `src/components/json-ld.tsx`, `serializeJsonLd` escapes `<`, `>`, `&`, U+2028/2029): the landing page has Organization + WebSite + WebPage + MobileApplication (Android from the package id; iOS only once `IOS_APP_STORE_ID` is set). Never add ratings, reviews, offers/prices or user counts. `/faq` has FAQPage built from the same `sections` and filters the page renders (`src/app/faq/plain-text.ts`), capped at 40 whole entries / 40k characters, no `hideInIosApp` sections; `faq-json-ld.test.ts` renders the page in every language and checks each marked-up answer equals the visible text.
- **Landing page** has a server-rendered feature section (`landing.features`, 8 blocks, every claim checked against the FAQ). Keep it honest: "verified" = email or phone confirmed before messaging, never ID verification; don't list gifts (admins only).
- **Sitemap/robots** (`src/app/sitemap.ts`, `robots.ts`, `sitemap-robots.test.ts`): sitemap lists public pages only (landing and FAQ once plain + once per language, each with all hreflang alternates), `lastModified` only for legal pages (`LEGAL_LAST_UPDATED` in seo.ts must match each page's "Last updated", the test reads it). robots disallows every session-guarded route (the test scans `src/app` for page guards) and one-time account steps. A new signed-in route must be added to robots' list or the test fails.
- **Store listings**: drafts in all nine languages in `docs/store-listing-drafts.md` (Swahili Play only), checked by `src/lib/store-listing-drafts.test.ts` (limits, keywords format, no competitor names). Search Console/Bing: `GOOGLE_SITE_VERIFICATION` / `BING_SITE_VERIFICATION` (see that doc's checklist).
